Resumo por domínio e pegadinhas da Terraform Associate

Como a prova pensa

A prova HashiCorp Certified: Terraform Associate (004) tem cerca de 50 a 60 questões em 60 minutos, baseadas no Terraform 1.12, misturando verdadeiro ou falso, múltipla escolha, múltipla resposta e preenchimento. Os enunciados são curtos e práticos: um cenário de equipe ou pipeline e a pergunta 'qual comando, opção, bloco ou argumento usar'. Muitas alternativas erradas são opções ou comandos inventados com nome plausível (-yes, -force, terraform fetch, hidden = true), e outras são recursos reais usados no lugar errado. A prova também valoriza as práticas recomendadas atuais: blocos declarativos (import, moved, removed), -replace no lugar de taint, -refresh-only no lugar de refresh, ephemeral e write-only para segredos. Pelos pesos de referência (a HashiCorp não publica pesos oficiais), Configuração (22,9%) e Fluxo de Trabalho Principal (17,5%) são os domínios com mais questões, somando cerca de 40% da prova.

Infraestrutura como Código com Terraform

  • Armadilha: Achar que uma configuração só pode ter recursos de um provedor de nuvem. Como evitar: Falso: é comum combinar nuvem, DNS, monitoramento, Kubernetes e Helm na mesma configuração.
  • Armadilha: Marcar 'executa os blocos na ordem do arquivo' como motivo de ser declarativo. Como evitar: A ordem vem das dependências (grafo). Declarativo é descrever o estado final.
  • Gatilho: se o enunciado traz “ambientes iguais várias vezes por semana”, pense em: Repetibilidade com a mesma configuração.
  • Gatilho: se o enunciado traz “homologação parecida com produção”, pense em: Mesmo código com variáveis/tfvars por ambiente.

Fundamentos do Terraform

  • Armadilha: Achar que ~> 5.1 aceita 6.x e 7.x. Como evitar: ~> trava o componente à esquerda do último informado: ~> 5.1 fica abaixo de 6.0.
  • Armadilha: Achar que o arquivo de lock não deve ir ao Git porque 'contém senhas' ou 'é recriado a cada plan'. Como evitar: O lock não contém senhas, não é recriado pelo plan e deve ser versionado.
  • Gatilho: se o enunciado traz “origem e versão de provider, hashicorp/aws ~> 5.0”, pense em: required_providers dentro de terraform.
  • Gatilho: se o enunciado traz “região padrão do provider”, pense em: Bloco provider.

Fluxo de Trabalho Principal

  • Armadilha: Achar que validate checa credenciais ou compara recursos reais com o estado. Como evitar: validate não acessa a nuvem; credenciais inválidas aparecem no plan/apply e comparar com a infraestrutura real é papel do plan.
  • Armadilha: Marcar 'falso' para 'validate precisa de init'. Como evitar: Verdadeiro: sem init não há providers para validar; em CI use init -backend=false.
  • Gatilho: se o enunciado traz “pipeline sem digitar yes”, pense em: -auto-approve.
  • Gatilho: se o enunciado traz “pipeline falhar em vez de esperar variável”, pense em: -input=false.

Configuração do Terraform

É o domínio de maior peso de referência (22,9%) e o mais cheio de sintaxe.

  • Armadilha: Achar que TF_VAR_ vence terraform.tfvars ou que default vence arquivos. Como evitar: Crescente: default < TF_VAR_ < terraform.tfvars < *.auto.tfvars < -var/-var-file.
  • Armadilha: Achar que sensitive = true impede gravar o segredo no estado. Como evitar: sensitive só oculta na saída; para tirar do estado use ephemeral ou write-only.
  • Gatilho: se o enunciado traz “valor com -var, tfvars e default ao mesmo tempo”, pense em: -var vence.
  • Gatilho: se o enunciado traz “a.auto.tfvars e b.auto.tfvars com a mesma variável”, pense em: b vence (ordem léxica).

Módulos do Terraform

  • Armadilha: Achar que o filho pode ler var.regiao do raiz diretamente. Como evitar: O filho não enxerga variáveis do pai; passe o valor como argumento no bloco module.
  • Armadilha: Achar que o app lê module.rede.subnet_id direto do irmão. Como evitar: Irmãos não se enxergam; o raiz conecta os dois.
  • Gatilho: se o enunciado traz “valor do filho para o pai”, pense em: output no filho + module.NOME.OUTPUT.
  • Gatilho: se o enunciado traz “valor do pai para o filho”, pense em: Argumento no bloco module.

Gerenciamento de State

  • Armadilha: Usar var.bucket no bloco backend. Como evitar: O backend é lido antes das variáveis; use configuração parcial com -backend-config.
  • Armadilha: Achar que o backend local não tem bloqueio ou que bloqueia outras máquinas. Como evitar: Tem bloqueio do sistema de arquivos, que só vale no disco local.
  • Gatilho: se o enunciado traz “estado bloqueado após execução interrompida”, pense em: terraform force-unlock ID_DO_LOCK.
  • Gatilho: se o enunciado traz “segunda pessoa esperar até 5 minutos”, pense em: -lock-timeout=5m.

Manutenção da Infraestrutura

  • Armadilha: Achar que terraform import da CLI cria o bloco resource em main.tf. Como evitar: Não gera código; para gerar, use bloco import com plan -generate-config-out.
  • Armadilha: Inverter a ordem: terraform import i-0abc123 aws_instance.web. Como evitar: Primeiro o endereço, depois o ID.
  • Gatilho: se o enunciado traz “recurso renomeado no código sem recriar”, pense em: Bloco moved (ou state mv).
  • Gatilho: se o enunciado traz “deixar de gerenciar sem destruir, revisável no plano”, pense em: removed com destroy = false.

HCP Terraform

  • Armadilha: Achar que o variable set vence a variável do workspace. Como evitar: O workspace vence por padrão; só o conjunto prioritário sobrepõe.
  • Armadilha: Escolher agentes para integrar ferramenta de segurança de terceiros. Como evitar: Agentes executam runs em redes privadas; integração com terceiros é run task.
  • Gatilho: se o enunciado traz “outra ferramenta envia configuração e dispara runs”, pense em: Fluxo orientado por API.
  • Gatilho: se o enunciado traz “commits e pull requests disparam runs”, pense em: Fluxo VCS.

Erros que mais custam pontos

  • Achar que sensitive = true tira o segredo do estado.
  • Errar a precedência de variáveis (TF_VAR_ perde para tfvars; -var vence tudo).
  • Confundir validate (sintaxe e referências) com fmt -check (estilo) e com plan (comparação com o mundo real).
  • Usar version em módulo Git ou local e achar que o lock guarda versões de módulos.

Plano de estudo para a Terraform Associate em 4 semanas

  1. Semana 1Faça a Prova 1 no tempo do exame (60 minutos), sem consulta, e anote o resultado por domínio.
  2. Semana 2Estude os domínios abaixo da nota de corte na documentação oficial e refaça as questões que errou.
  3. Semana 3Faça as provas 2 a 4, lendo a explicação de todas as alternativas, inclusive das que acertou. Armadilha frequente nesse domínio: Achar que uma configuração só pode ter recursos de um provedor de nuvem.
  4. Semana 4Faça as provas 5 e 6 e agende o exame quando estiver em 80% ou mais (a referência é 70%). Na última semana: refaça as provas práticas e anote cada opção de comando que errou em uma lista única de flags (init, plan, apply, fmt, state).

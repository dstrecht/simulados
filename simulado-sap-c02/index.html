Questão 1 · Aceleração da migração e da modernização de workloads

Uma instituição educacional está migrando rapidamente dezenas de aplicações web legadas para a AWS. A equipe de arquitetura deseja padronizar a criação de redes, contas, pipelines de CI/CD e padrões de observabilidade, minimizando retrabalho e garantindo que novos times possam provisionar ambientes de forma consistente e segura. Qual combinação de serviços e abordagens é MAIS apropriada para acelerar essa migração e modernização, mantendo boas práticas de arquitetura?

  1. Utilizar Amazon Lightsail para provisionar rapidamente instâncias para cada aplicação, com segurança e redes configuradas individualmente por cada time, e integrar a implantação à mão via Git hooks
  2. Criar uma única conta AWS compartilhada para os ambientes, com servidores provisionados por scripts próprios
  3. Utilizar AWS Elastic Beanstalk para as aplicações, configurando à mão VPCs, sub-redes e roles IAM em cada conta, e deixando que cada time implemente seu próprio pipeline de CI/CD com ferramentas diversas
  4. Usar o Control Tower para contas e guardrails, o Service Catalog para blueprints de rede e aplicação e pipelines padronizados no CodePipeline
Ver resposta comentada

Resposta: D) Usar o Control Tower para contas e guardrails, o Service Catalog para blueprints de rede e aplicação e pipelines padronizados no CodePipeline

Resposta correta: Usar o Control Tower para contas e guardrails, o Service Catalog para blueprints de rede e aplicação e pipelines padronizados no CodePipeline

Por quê: Esta alternativa é a mais adequada porque combina serviços voltados especificamente para aceleração e padronização de migração em escala. O AWS Control Tower facilita a criação e governança de múltiplas contas com guardrails e boas práticas de segurança. O AWS Service Catalog, apoiado por AWS CloudFormation, permite publicar blueprints padronizados de redes (VPC, sub-redes, segurança) e de aplicações, que podem ser reutilizados por diferentes times.

Dica de prova: Para migração e modernização em escala, pense em três pilares: (1) Governança multi-conta (AWS Organizations, Control Tower), (2) Infraestrutura como código e catálogos padronizados (CloudFormation, Service Catalog) e (3) Pipelines de CI/CD reutilizáveis (CodePipeline, CodeBuild, CodeDeploy).

Questão 2 · Design de novas soluções

Uma empresa de mídia digital deseja lançar uma nova plataforma de distribuição de vídeos sob demanda (VoD) em múltiplas regiões da AWS. Os requisitos incluem: (1) baixa latência global para streaming, (2) alta disponibilidade e resiliência a falhas regionais, (3) capacidade de personalizar recomendações de conteúdo por usuário, (4) minimização de esforço operacional na camada de backend, e (5) custos previsíveis para o ambiente de produção. Como um Solutions Architect deve projetar a solução principal de backend para atender a esses requisitos?

  1. Criar uma arquitetura híbrida com frontends servidos por CloudFront e S3, backend principal em servidores on-premises conectados à AWS via AWS Direct Connect, e utilizar Amazon RDS for PostgreSQL Multi-AZ só para armazenar logs de acesso, mantendo toda a lógica de personalização e metadados de usuários no datacenter local para reduzir custos de armazenamento na nuvem.
  2. Provisionar um cluster de Kubernetes no Amazon EKS em uma única região com múltiplas zonas de disponibilidade, executar os microserviços de backend (catálogo, perfis, recomendações) em pods containerizados acessando um banco de dados PostgreSQL em Amazon RDS Single-AZ, e usar CloudFront para distribuição de vídeos a partir de um bucket S3 regional.
  3. Usar API Gateway e Lambda para a lógica, DynamoDB global tables para metadados e perfis, CloudFront com origem no S3 para o streaming HLS e DASH e failover entre regiões pelo Route 53 com health checks
  4. Criar uma arquitetura baseada em microserviços executando em Amazon ECS com Fargate em duas regiões, utilizando Application Load Balancer com failover DNS via Amazon Route 53.

Resposta: C) Usar API Gateway e Lambda para a lógica, DynamoDB global tables para metadados e perfis, CloudFront com origem no S3 para o streaming HLS e DASH e failover entre regiões pelo Route 53 com health checks

A equipe de TI quer minimizar mudanças de código, acelerar a movimentação em massa e, ao mesmo tempo, criar uma base que facilite modernizações futuras para serviços gerenciados e arquitetura de microsserviços.   4. Reescrever as aplicações Java em microsserviços usando AWS Lambda e Amazon API Gateway antes da migração, aproveitando o prazo de 9 meses para eliminar os componentes legados e descontinuar o uso de servidores de aplicação.

Questão 8 · Soluções de design de complexidade organizacional

A diretoria quer: (1) padronizar a governança e segurança em todas as contas, (2) manter alguma autonomia operacional por região, (3) reduzir o esforço para criação de novas contas e (4) garantir trilha de auditoria centralizada. Como o arquiteto de soluções deve projetar a solução de forma mais adequada?

  1. Criar uma única conta AWS monolítica para os workloads globais, migrar os recursos das demais contas para essa conta, aplicar políticas IAM detalhadas por time.
  2. Usar AWS Single Sign-On (IAM Identity Center) para unificar o acesso a as contas, mantendo cada conta com sua própria configuração independente de logs e políticas de segurança. Criar um CloudFormation StackSet só para padronizar grupos e funções IAM nas contas existentes.
  3. Criar uma conta central de segurança e habilitar AWS CloudTrail e AWS Config só nesta conta. Compartilhar os mesmos logs com as contas por meio de AWS Resource Access Manager (AWS RAM), mantendo as políticas de segurança e SCP geridas localmente em cada conta para maior autonomia.
  4. Organizar OUs por região e ambiente com SCPs padronizadas, centralizar CloudTrail e Config em uma conta de segurança e usar o Control Tower para padronizar contas novas

Resposta: D) Organizar OUs por região e ambiente com SCPs padronizadas, centralizar CloudTrail e Config em uma conta de segurança e usar o Control Tower para padronizar contas novas

Resposta correta: Organizar OUs por região e ambiente com SCPs padronizadas, centralizar CloudTrail e Config em uma conta de segurança e usar o Control Tower para padronizar contas novas

Por quê: Esta alternativa é a mais adequada porque usa o AWS Organizations para criar uma hierarquia de OUs, permitindo padronizar governança e segurança via SCPs e, ao mesmo tempo, manter autonomia operacional por região e ambiente. A centralização de logs de AWS CloudTrail e AWS Config em uma conta de segurança dedicada garante auditoria consistente e separação de deveres.

Dica de prova: Para cenários com múltiplas contas e requisitos de conformidade, pense em: (1) AWS Organizations + OUs para governança, (2) SCPs para limites de segurança, (3) conta central de segurança/logs e (4) ferramentas como AWS Control Tower ou Account Factory para padronizar a criação de contas.

Resposta: C) Utilizar Amazon Data Firehose para ingerir e entregar os dados diretamente em tabelas externas no Amazon Athena, armazenando os arquivos brutos comprimidos no Amazon S3.

Resposta correta: Utilizar Amazon Data Firehose para ingerir e entregar os dados diretamente em tabelas externas no Amazon Athena, armazenando os arquivos brutos comprimidos no Amazon S3.

  2. Criar snapshots manuais diários de bancos de dados e volumes de dados, copiá-los para outra região e documentar um procedimento de recuperação manual a ser executado só em caso de desastre
  3. Mover a aplicação para uma única zona de disponibilidade em uma região diferente e utilizar instâncias maiores, reduzindo a superfície de falha e simplificando o plano de recuperação de desastres
  4. Habilitar AWS Backup para os recursos em uso e configurar políticas de retenção em múltiplos tiers de armazenamento
Ver resposta comentada

Resposta: A) Adotar ativo-ativo em duas regiões com o Global Accelerator, replicação assíncrona dos dados e game days regulares de falha regional

Resposta correta: Adotar ativo-ativo em duas regiões com o Global Accelerator, replicação assíncrona dos dados e game days regulares de falha regional

Questão 12 · Soluções de design de complexidade organizacional

Uma organização global está padronizando o uso de AWS Organizations para gerenciar dezenas de contas AWS pertencentes a diferentes unidades de negócio. O time de arquitetura quer aplicar políticas centralizadas que imponham requisitos mínimos de segurança (como proibição de desativar CloudTrail e uso obrigatório de chaves KMS gerenciadas pela organização), mas também precisa permitir que cada unidade de negócio tenha autonomia para criar políticas adicionais mais restritivas quando necessário. Qual abordagem de design atende melhor a esses requisitos?

  1. Criar uma conta de segurança dedicada, mover os recursos críticos para essa conta e não utilizar AWS Organizations.
  2. Desligar o uso de SCPs no nível da Organization e delegar por completo a gestão de IAM para cada conta, utilizando só políticas de IAM e permissões baseadas em tags.
  3. Usar uma hierarquia de OUs, com SCPs de controles mínimos no topo e SCPs mais restritivas das unidades em OUs filhas
  4. Criar uma única SCP no nível da raiz da Organization, contendo as regras atuais e futuras de segurança, e anexá-la a as contas, impedindo que unidades de negócio utilizem SCPs próprias.
Ver resposta comentada

Resposta: C) Usar uma hierarquia de OUs, com SCPs de controles mínimos no topo e SCPs mais restritivas das unidades em OUs filhas

Resposta correta: Usar uma hierarquia de OUs, com SCPs de controles mínimos no topo e SCPs mais restritivas das unidades em OUs filhas

Por quê: Esta alternativa é a mais adequada porque usa o modelo recomendado pela AWS para ambientes multi-contas: uma hierarquia de OUs com Service Control Policies (SCPs) aplicadas em camadas. As SCPs nas OUs de nível superior definem a 'linha de base' de segurança (por exemplo, impedir desativação de CloudTrail, exigir uso de KMS gerenciado centralmente), enquanto as unidades de negócio podem anexar SCPs adicionais, mais restritivas, em OUs filhas ou diretamente nas contas.

Dica de prova: Pense nas SCPs como um "teto máximo de permissões" por OU ou conta. O ideal é usar uma OU raiz com políticas de baseline (segurança mínima obrigatória) e depois especializar por unidade de negócio com SCPs adicionais mais restritivas, nunca mais permissivas.

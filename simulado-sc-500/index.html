Questão 1 · Gerenciar e monitorar a postura de segurança

O Grupo Educacional Ponto Alto usa Windows Event Forwarding para centralizar os eventos de segurança dos servidores em um coletor (WEC), e envia ao Microsoft Sentinel pelo conector Windows Forwarded Events via AMA. Os eventos chegam ao workspace, mas várias regras de análise internas de segurança do Windows nunca disparam. Qual é a causa provável?

  1. As regras internas só funcionam com o agente legado do Log Analytics instalado no próprio coletor WEC
  2. O conector Windows Forwarded Events só aceita eventos do log de Aplicativo, não do log de Segurança
  3. O coletor WEC remove os IDs de evento originais ao encaminhar, impedindo a correlação nas regras
  4. Os eventos encaminhados vão para a tabela WindowsEvent, e as regras internas consultam SecurityEvent
Ver resposta comentada

Resposta: D) Os eventos encaminhados vão para a tabela WindowsEvent, e as regras internas consultam SecurityEvent

Resposta correta: Os eventos encaminhados vão para a tabela WindowsEvent, e as regras internas consultam SecurityEvent

Por quê: Windows Event Forwarding envia eventos a um coletor WEC; com o AMA no coletor, o conector Windows Forwarded Events ingere esses eventos na tabela WindowsEvent. Regras de segurança que consultam SecurityEvent precisam ser adaptadas ou os servidores devem usar o conector Windows Security Events via AMA.

Dica de prova: Eventos via WEF caem em WindowsEvent, não em SecurityEvent: ajuste as regras.

Referência: Conjuntos de eventos de segurança do Windows no Sentinel

Questão 2 · Gerenciar identidade, acesso e governança

A Cooperativa de Crédito Vale Verde já acessa seu Azure Key Vault por ponto de extremidade privado e vai mudar Acesso à rede pública para Desabilitado. Hoje o firewall do cofre tem uma regra de IP para um pipeline do Azure DevOps com agentes hospedados pela Microsoft e a exceção Permitir serviços confiáveis da Microsoft habilitada. O que acontece após a mudança?

  1. A regra de IP e os serviços confiáveis passam a exigir um ponto de extremidade privado próprio
  2. A regra de IP deixa de valer e o pipeline é bloqueado; os serviços confiáveis continuam acessando o cofre
  3. Nada muda, porque desabilitar o acesso público afeta só as operações do plano de controle do cofre
  4. A regra de IP continua valendo para o pipeline, mas os serviços confiáveis passam a ser bloqueados
Ver resposta comentada

Resposta: B) A regra de IP deixa de valer e o pipeline é bloqueado; os serviços confiáveis continuam acessando o cofre

Resposta correta: A regra de IP deixa de valer e o pipeline é bloqueado; os serviços confiáveis continuam acessando o cofre

Por quê: Desabilitar o acesso público no Key Vault deixa só pontos de extremidade privados e a exceção de serviços confiáveis; serviços fora da lista, como o Azure DevOps, precisam de rede privada (por exemplo, agentes auto-hospedados em VNet).

Dica de prova: Acesso público Desabilitado: regras de IP param, serviços confiáveis seguem; Secure by perimeter bloqueia até os confiáveis.

Referência: Segurança de rede do Azure Key Vault

Questão 3 · Proteger a computação

Uma API de back-end publicada no API Management de uma seguradora deve aceitar apenas tokens emitidos pelo locatário Microsoft Entra da empresa e só de dois aplicativos clientes específicos. Qual política aplicar de forma mais direta?

  1. ip-filter com os endereços IP públicos dos dois aplicativos clientes
  2. validate-azure-ad-token com tenant-id e client-application-ids dos dois aplicativos
  3. rate-limit-by-key usando o ID do aplicativo cliente como chave
  4. check-header exigindo o cabeçalho Authorization em cada chamada
Ver resposta comentada

Resposta: B) validate-azure-ad-token com tenant-id e client-application-ids dos dois aplicativos

Resposta correta: validate-azure-ad-token com tenant-id e client-application-ids dos dois aplicativos

Por quê: validate-azure-ad-token é a política do API Management específica para tokens do Microsoft Entra: basta o tenant-id, com elementos como client-application-ids, audiences e required-claims. Para outros provedores de identidade, usa-se validate-jwt com openid-config.

Dica de prova: Token do Entra no APIM = validate-azure-ad-token; outros provedores = validate-jwt.

Referência: Política validate-azure-ad-token

Questão 4 · Proteger armazenamento, bancos de dados e redes

A Metalúrgica Forte Aço vai implantar um Azure Firewall Standard na VNet hub, e a política corporativa exige que todo o tráfego de internet inspecionado pelo firewall siga para o firewall de borda do datacenter local, por uma rota padrão 0.0.0.0/0 em UDR ou anunciada por BGP, sem que o Azure perca a capacidade de gerenciar o firewall. O que é necessário na implantação?

  1. Usar o SKU Basic, único que permite túnel forçado, e aplicar a rota padrão na sub-rede AzureFirewallSubnet sem outras mudanças
  2. Implantar o firewall sem nenhum IP público e sem sub-rede de gerenciamento, já que o tráfego de saída vai para o datacenter
  3. Habilitar a interface de gerenciamento, com a sub-rede AzureFirewallManagementSubnet de pelo menos /26 e um IP público próprio
  4. Associar à sub-rede AzureFirewallManagementSubnet uma tabela de rotas com 0.0.0.0/0 apontando para o firewall do datacenter
Ver resposta comentada

Resposta: C) Habilitar a interface de gerenciamento, com a sub-rede AzureFirewallManagementSubnet de pelo menos /26 e um IP público próprio

Resposta correta: Habilitar a interface de gerenciamento, com a sub-rede AzureFirewallManagementSubnet de pelo menos /26 e um IP público próprio

Por quê: No túnel forçado do Azure Firewall, o tráfego para a internet segue uma rota padrão (UDR ou BGP) até um NVA ou firewall local. Para isso, o firewall precisa da interface de gerenciamento, que usa a AzureFirewallManagementSubnet (/26 ou maior) e um IP público usado só pela plataforma Azure.

Dica de prova: Túnel forçado no Azure Firewall: NIC de gerenciamento + AzureFirewallManagementSubnet /26 com IP público próprio.

Referência: Interface de gerenciamento do Azure Firewall

Questão 5 · Gerenciar e monitorar a postura de segurança

Um firewall de terceiros de uma empresa de energia só envia logs em CEF por Syslog. O SOC quer esses eventos na tabela CommonSecurityLog do Microsoft Sentinel, seguindo a arquitetura atual suportada. O que implantar?

  1. Encaminhador Linux com o agente do Azure Monitor e a DCR do conector CEF via AMA
  2. Encaminhador Linux com o agente OMS e o conector CEF legado
  3. Encaminhador Windows com o agente do Log Analytics gravando na tabela Syslog do workspace
  4. Envio direto do firewall ao workspace por HTTPS, sem encaminhador
Ver resposta comentada

Resposta: A) Encaminhador Linux com o agente do Azure Monitor e a DCR do conector CEF via AMA

Resposta correta: Encaminhador Linux com o agente do Azure Monitor e a DCR do conector CEF via AMA

Por quê: No conector CEF via AMA, uma máquina Linux (VM do Azure ou servidor com Azure Arc) atua como encaminhador: o script de instalação configura rsyslog ou syslog-ng para escutar na porta 514, e a DCR define facilidades e severidades. Usar a mesma facilidade para CEF e Syslog pode duplicar dados.

Dica de prova: CEF no Sentinel = encaminhador Linux + AMA + DCR, tabela CommonSecurityLog.

Referência: Ingerir Syslog e CEF com o AMA

Questão 6 · Gerenciar identidade, acesso e governança

Na holding Trevo, o time de plataforma quer que líderes de aplicação criem atribuições de função nos próprios grupos de recursos, mas só das funções Storage Blob Data Reader e Website Contributor e só para grupos, nunca para usuários individuais. Qual solução atende?

  1. Owner no grupo de recursos combinado com atribuição de negação para as demais funções
  2. Função personalizada com NotActions em Microsoft.Authorization/* no grupo de recursos
  3. User Access Administrator atribuído no grupo de recursos de cada aplicação, sem condição
  4. Role Based Access Control Administrator com condição de funções e tipos
Ver resposta comentada

Resposta: D) Role Based Access Control Administrator com condição de funções e tipos

Resposta correta: Role Based Access Control Administrator com condição de funções e tipos

Por quê: Delegar o gerenciamento de atribuições com condições permite restringir funções, tipos de entidade e até entidades específicas, aplicando menor privilégio a quem atribui acessos.

Dica de prova: Delegar atribuição de função com limites = RBAC Administrator + condição (funções e tipos de entidade).

Referência: Delegar atribuições de função com condições

Questão 7 · Proteger a computação

A Indústria Química Delta quer habilitar Trusted Launch em uma VM de Geração 2 existente, protegida pelo Azure Backup com a política Standard. O tamanho e o sistema operacional da VM são suportados. O que precisa ser feito para concluir a alteração do tipo de segurança?

  1. Converter a VM para Geração 1, desalocar a VM e mudar o tipo de segurança para Trusted Launch com vTPM
  2. Manter a VM em execução e ativar Trusted Launch na hora, pois a troca do tipo de segurança é feita a quente
  3. Migrar o backup para a política Enhanced, desalocar a VM e mudar o tipo de segurança para Trusted Launch
  4. Recriar a VM a partir de uma imagem nova, pois VMs existentes não podem receber Trusted Launch em nenhum caso
Ver resposta comentada

Resposta: C) Migrar o backup para a política Enhanced, desalocar a VM e mudar o tipo de segurança para Trusted Launch

Resposta correta: Migrar o backup para a política Enhanced, desalocar a VM e mudar o tipo de segurança para Trusted Launch

Por quê: Para habilitar Trusted Launch em uma VM de Geração 2 existente, o tamanho e o SO precisam ser suportados, o backup (se houver) deve usar a política Enhanced e a VM deve ser desalocada antes de mudar o tipo de segurança de Standard para Trusted Launch.

Dica de prova: Trusted Launch em VM existente: Gen2, backup Enhanced, VM desalocada.

Referência: Habilitar Trusted Launch em VMs Gen2 existentes

Questão 8 · Proteger armazenamento, bancos de dados e redes

A loja virtual Casa e Lar habilitou o Defender for Azure SQL. Um alerta "Potential SQL injection" foi gerado, mas só o proprietário da assinatura recebeu e-mail; o time de DBAs não. Como fazer o time receber por e-mail os alertas de severidade média ou maior?

  1. Criar uma regra de alerta de métrica no Azure Monitor sobre o uso de CPU do banco de dados afetado
  2. Incluir os e-mails do time em Notificações por e-mail do Defender for Cloud e escolher severidade Média
  3. Habilitar a auditoria do servidor lógico com destino direto ao endereço de e-mail do time de DBAs da empresa
  4. Atribuir ao time a função Security Reader na assinatura para que passe a receber os alertas por e-mail
Ver resposta comentada

Resposta: B) Incluir os e-mails do time em Notificações por e-mail do Defender for Cloud e escolher severidade Média

Resposta correta: Incluir os e-mails do time em Notificações por e-mail do Defender for Cloud e escolher severidade Média

Por quê: Os alertas do Defender for Cloud (como Potential SQL injection e A possible vulnerability to SQL Injection) seguem as notificações por e-mail da assinatura, configuráveis com destinatários adicionais e severidade mínima.

Dica de prova: Quem recebe alerta por e-mail se configura em Notificações por e-mail do Defender for Cloud (destinatários e severidade).

Referência: Notificações por e-mail do Defender for Cloud

Questão 10 · Gerenciar identidade, acesso e governança

O cofre kv-integracoes da Têxtil Vale guarda segredos de 15 integrações e foi migrado do modelo de políticas de acesso para o Azure RBAC, porque usuários com Contributor podiam conceder a si mesmos acesso ao plano de dados. O aplicativo de faturamento, com identidade gerenciada, deve ler somente o segredo erp-api-key. Como conceder o menor privilégio?

  1. Atribuir Key Vault Reader à identidade no cofre, pois ela permite ler o valor dos segredos
  2. Atribuir Key Vault Secrets User à identidade com escopo no próprio segredo erp-api-key
  3. Criar uma política de acesso com a permissão Get de segredos para a identidade no cofre
  4. Atribuir Key Vault Secrets Officer à identidade com escopo no grupo de recursos do cofre
Ver resposta comentada

Resposta: B) Atribuir Key Vault Secrets User à identidade com escopo no próprio segredo erp-api-key

Resposta correta: Atribuir Key Vault Secrets User à identidade com escopo no próprio segredo erp-api-key

Por quê: O Azure RBAC do Key Vault aceita atribuições em grupo de gerenciamento, assinatura, grupo de recursos, cofre e também em chaves, segredos e certificados individuais. Para leitura de um único segredo, Key Vault Secrets User no escopo do segredo é o menor privilégio.

Dica de prova: Um app, um segredo: Key Vault Secrets User no escopo do segredo. Key Vault Reader não lê valores.

Referência: Azure RBAC para o Key Vault

Questão 11 · Proteger a computação

A fintech Arrecada quer que um agente de IA receba associação a um grupo de segurança que libera uma API interna por 90 dias, com aviso ao patrocinador do agente antes do vencimento e possibilidade de pedir extensão. Qual abordagem do Microsoft Entra atende?

  1. Revisão de acesso trimestral no grupo de segurança, sem nenhum pacote de acesso associado ao agente
  2. Atribuição permanente de uma função de aplicativo (app role) ao agente no aplicativo empresarial da API
  3. Segredo do cliente com validade de 90 dias adicionado ao blueprint de identidade do agente de IA
  4. Pacote de acesso do gerenciamento de direitos com política que permite agentes e atribuição com expiração
Ver resposta comentada

Resposta: D) Pacote de acesso do gerenciamento de direitos com política que permite agentes e atribuição com expiração

Resposta correta: Pacote de acesso do gerenciamento de direitos com política que permite agentes e atribuição com expiração

Por quê: O gerenciamento de direitos permite atribuir pacotes de acesso a identidades de agente com grupos de segurança, funções de diretório permitidas e permissões de API, sempre com prazo e acompanhamento do patrocinador.

Dica de prova: Acesso com prazo para agente = pacote de acesso (entitlement management) com patrocinador notificado.

Referência: Pacotes de acesso para agentes

Questão 12 · Proteger armazenamento, bancos de dados e redes

Uma empresa de energia exige girar as chaves de acesso das contas de armazenamento a cada 90 dias e quer que as contas com chaves vencidas apareçam como não conformes em um relatório central. O que configurar?

  1. Exclusão temporária de blobs com 90 dias de retenção em cada conta de armazenamento
  2. Lembrete de rotação de 90 dias em cada conta e a política Storage account keys should not be expired
  3. Política de expiração de chaves de 90 dias, que desabilita a chave vencida até que ela seja girada pelo administrador
  4. Política de expiração de SAS de 90 dias com ação Block nas contas de armazenamento
Ver resposta comentada

Resposta: B) Lembrete de rotação de 90 dias em cada conta e a política Storage account keys should not be expired

Resposta correta: Lembrete de rotação de 90 dias em cada conta e a política Storage account keys should not be expired

Por quê: A política de expiração de chaves (keyExpirationPeriodInDays), configurada pelo lembrete de rotação, define quando as chaves de acesso devem ser giradas, mas não as desativa. Para relatar conformidade, usa-se a política interna Storage account keys should not be expired. Contas antigas podem precisar girar as chaves uma vez antes de aceitar o lembrete.

Dica de prova: Lembrete de rotação de chave de Storage não desativa a chave; a conformidade vem do Azure Policy.

Referência: Gerenciar as chaves de acesso da conta de armazenamento

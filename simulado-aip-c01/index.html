Questão 1 de 12 · Domínio 1: Integração de modelos de base, gestão de dados e conformidade

Uma seguradora indexou suas condições gerais de apólice em uma base de conhecimento do Amazon Bedrock com chunking de tamanho fixo e sem sobreposição. Nas avaliações, respostas que dependem de uma cláusula e da exceção que vem logo em seguida saem incompletas: a recuperação traz o trecho com a cláusula, mas a exceção ficou no trecho seguinte. Qual ajuste de baixo esforço reduz esse problema?

Resposta: B) Configurar uma porcentagem de sobreposição entre trechos consecutivos no chunking fixo e refazer a ingestão dos documentos

Por quê: No chunking de tamanho fixo das Amazon Bedrock Knowledge Bases, o máximo de tokens por trecho e a porcentagem de sobreposição definem onde o texto é cortado. A sobreposição faz trechos vizinhos compartilharem parte do conteúdo, o que reduz a perda de informações que atravessam o limite entre eles; o chunking hierárquico é outra opção quando o modelo precisa do contexto maior do trecho pai.

Dica de prova: Informação cortada entre trechos vizinhos: sobreposição (ou chunking hierárquico).

Referência: Knowledge Bases: estratégias de chunking

Questão 2 de 12 · Domínio 2: Implementação e integração

Uma editora expõe por uma REST API regional do Amazon API Gateway a geração de capítulos de material didático, que leva de 3 a 8 minutos por pedido e hoje passa por uma Lambda síncrona que expira. Os clientes aceitam consultar o andamento periodicamente. A arquitetura quer eliminar a Lambda intermediária e acompanhar cada pedido com estado e histórico de execução. Qual solução atende a esses requisitos?

Resposta: C) Integrar o POST direto à StartExecution de uma máquina Standard do Step Functions, devolver o executionArn como ID da tarefa e expor um GET de status ligado à DescribeExecution

Por quê: Gerações longas não cabem no tempo limite de integração do API Gateway. O padrão assíncrono responde na hora com um ID de tarefa e oferece um endpoint de status: com Step Functions, o API Gateway chama StartExecution direto (devolve o executionArn) e DescribeExecution informa estado e saída, com histórico de cada execução.

Dica de prova: Geração de minutos atrás do API Gateway: responda com ID de tarefa (StartExecution) e exponha status (DescribeExecution). StartSyncExecution continua síncrono.

Referência: Step Functions: criar uma API com o API Gateway

Questão 3 de 12 · Domínio 3: Segurança, proteção e governança de IA

Um banco alimenta uma base de conhecimento do Amazon Bedrock com textos gerados por jobs Spark do AWS Glue 5.0, que leem tabelas catalogadas no AWS Glue Data Catalog, mascaram dados pessoais e gravam o resultado no bucket da fonte de dados. O auditor quer ver, de forma visual e sem planilhas mantidas pela equipe, o caminho de cada conjunto de dados desde as tabelas de origem até o prefixo indexado, com as transformações e as colunas envolvidas. A área de dados já tem um domínio do Amazon SageMaker Unified Studio. Qual solução atende a esse requisito com o MENOR esforço?

Resposta: D) Habilitar nos jobs do Glue a emissão de eventos de linhagem (OpenLineage) para o domínio do SageMaker Unified Studio, que monta de forma automática o grafo da origem ao destino, com linhagem por coluna

Por quê: Linhagem de dados responde de onde o dado veio e como foi transformado. Jobs Spark do AWS Glue podem emitir eventos OpenLineage capturados pelo Amazon SageMaker Unified Studio, que exibe o grafo de origem até o destino, inclusive por coluna, e guarda versões no tempo. O Data Catalog registra os conjuntos de dados, e o CloudTrail registra quem chamou quais APIs, que são evidências diferentes.

Dica de prova: Auditor quer o caminho fonte, transformação e índice: linhagem automática dos jobs do Glue (OpenLineage). Catálogo registra, CloudTrail audita chamadas.

Referência: SageMaker Unified Studio: suporte a linhagem de dados

Questão 4 de 12 · Domínio 4: Eficiência operacional e otimização de aplicações de IA generativa

Você é responsável pela operação de um serviço de geração de código baseado em um modelo de fundação hospedado no Amazon Bedrock. Nas últimas semanas, o custo de inferência aumentou 40%, embora o volume de requisições tenha crescido apenas 10%. A análise preliminar mostra que: - A maioria das requisições vem de um endpoint REST público no Amazon API Gateway. - Vários clientes estão enviando prompts muito longos e pedindo respostas extensas. - Há picos de tráfego imprevisíveis durante o horário comercial. Você precisa otimizar a eficiência operacional e reduzir custos, mantendo boa experiência do desenvolvedor e mínima mudança na API pública. Qual combinação de ações é MAIS adequada?

Resposta: C) Usar uma Lambda intermediária que normaliza e limita prompts, aplica maxTokens por tipo de cliente e mede tokens por cliente, com usage plans na API

Por quê: Em aplicações de GenAI, o custo acompanha os tokens. Uma camada intermediária que normaliza prompts, limita maxTokens por perfil e mede o consumo por cliente, combinada com usage plans e throttling do API Gateway, reduz custo e protege contra picos sem alterar a API pública.

Dica de prova: Custo de LLM subindo mais que o volume: olhe os tokens por requisição, de entrada e de saída, antes de mexer em capacidade.

Referência: Parâmetros de inferência no Amazon Bedrock

Questão 5 de 12 · Domínio 5: Testes, validação e solução de problemas

Uma plataforma de educação gera feedback de redações com um modelo do Amazon Bedrock, acessado por uma API REST do Amazon API Gateway integrada a funções AWS Lambda. Em produção, algumas requisições retornam respostas truncadas ou vazias, mas o comportamento não se reproduz em teste. Não há exceções registradas no código das funções. Qual abordagem é a MAIS adequada para diagnosticar a causa raiz de forma sistemática?

Resposta: D) Ativar o tracing do X-Ray no API Gateway e nas Lambdas, registrar em logs estruturados o stopReason e os tokens de cada resposta e comparar a duração com o timeout de integração do API Gateway

Por quê: Respostas truncadas ou vazias sem exceção no código costumam vir do limite de tokens de saída (stopReason igual a max_tokens), de intervenção de guardrail ou filtro de conteúdo, ou do tempo limite de integração do API Gateway, que devolve erro ao cliente enquanto a Lambda ainda executa. Traces ponta a ponta e logs estruturados com stopReason e contagem de tokens separam essas causas.

Dica de prova: Resposta cortada sem exceção: olhe o stopReason, os tokens e o timeout de integração do API Gateway, com traces ponta a ponta.

Referência: AWS X-Ray: tracing ponta a ponta

Questão 6 de 12 · Domínio 1: Integração de modelos de base, gestão de dados e conformidade

Uma startup de educação ajustou um modelo da família Amazon Nova no Amazon Bedrock para corrigir redações. O uso é baixo e irregular: picos em semanas de prova e dias inteiros sem requisições. Hoje o modelo ajustado é servido com Provisioned Throughput sem compromisso, e a conta mensal é dominada pelas horas ociosas. A startup quer reduzir o custo mantendo o modelo customizado. Qual solução atende a esses requisitos com o MENOR esforço operacional?

Resposta: D) Criar uma implantação sob demanda do modelo customizado e usar o ARN da implantação como modelId nas chamadas, pagando pelos tokens processados

Por quê: Implantação sob demanda de modelo customizado: depois de ajustar um modelo suportado no Bedrock, é possível criar uma custom model deployment e invocá-la pelo ARN como modelId, pagando pelo uso. Para tráfego baixo e irregular, isso elimina o custo de horas ociosas do Provisioned Throughput.

Dica de prova: Modelo ajustado com tráfego esporádico: implantação sob demanda (ARN da deployment como modelId). Provisioned Throughput só compensa com uso alto e constante.

Referência: Implantar modelo customizado para inferência sob demanda

Questão 7 de 12 · Domínio 2: Implementação e integração

Uma editora de livros didáticos orquestra no AWS Step Functions a criação de apostilas com IA generativa. Uma etapa envia o material a um serviço de diagramação em contêineres no Amazon ECS que pode levar até duas horas. Hoje uma função AWS Lambda fica consultando o status em laço, esbarra no limite de 15 minutos e é reinvocada várias vezes, gerando custo com espera ociosa. A equipe quer que o fluxo aguarde o fim do job sem nenhuma função ativa esperando. Qual solução atende a esses requisitos?

Resposta: A) Usar uma tarefa com .waitForTaskToken que envia o task token ao job, por exemplo em uma mensagem do SQS, e fazer o job chamar SendTaskSuccess ao terminar

Por quê: O padrão Wait for Callback (.waitForTaskToken) de um Standard Workflow permite que o Step Functions entregue um token a um processo externo e espere, por até um ano, que esse processo devolva o resultado. Assim, jobs longos de geração ou de processamento não exigem funções esperando nem polling.

Dica de prova: Job externo longo no Step Functions: .waitForTaskToken + SendTaskSuccess, sem Lambda esperando.

Referência: Padrões de integração de serviços do Step Functions

Questão 8 de 12 · Domínio 3: Segurança, proteção e governança de IA

Uma empresa farmacêutica guarda em um bucket do Amazon S3 os estudos clínicos que alimentam um pipeline próprio de RAG. A ingestão roda em tarefas do Amazon ECS em sub-redes privadas, que acessam o S3 por um endpoint de gateway da VPC. A segurança exige que os objetos do bucket sejam lidos somente por requisições que passem por esse endpoint, mesmo que alguma credencial com permissão de leitura vaze para fora da VPC. Qual configuração atende a esse requisito?

Resposta: B) Adicionar à política do bucket uma instrução Deny para s3:GetObject com a condição StringNotEquals em aws:SourceVpce igual ao ID do endpoint, mantendo a permissão de leitura na role das tarefas

Por quê: Perímetro de dados para o acervo de RAG combina permissão de identidade com uma condição de rede na política do recurso. aws:SourceVpce na política do bucket garante que o acesso só ocorra pelo endpoint da VPC, protegendo contra credenciais vazadas.

Dica de prova: Bucket lido só pelo endpoint da VPC: Deny com StringNotEquals em aws:SourceVpce; cuidado, isso também bloqueia o console e serviços fora da VPC.

Referência: Controlar o acesso de endpoints da VPC com políticas de bucket

Questão 9 de 12 · Domínio 4: Eficiência operacional e otimização de aplicações de IA generativa

O assistente de suporte de uma operadora de internet reenvia ao modelo do Amazon Bedrock o histórico completo da conversa a cada turno. Em atendimentos longos, os tokens de entrada por requisição crescem a cada mensagem e o custo por conversa triplicou, embora as perguntas finais dependam pouco dos primeiros turnos. A empresa definiu um orçamento máximo de tokens de entrada por requisição e quer manter o contexto relevante. Qual solução atende a esses requisitos?

Resposta: B) Manter os últimos turnos completos e trocar os anteriores por um resumo acumulado, gerado por um modelo menor e guardado com a sessão, conferindo com CountTokens se o prompt cabe no orçamento

Por quê: Gestão de contexto em conversas longas combina janela deslizante dos turnos recentes com resumos dos anteriores, mantendo o prompt dentro de um orçamento de tokens. Contar tokens com o tokenizador do modelo (CountTokens) evita estimativas erradas.

Dica de prova: Histórico crescendo e encarecendo cada turno: janela dos últimos turnos + resumo dos antigos + CountTokens para respeitar o orçamento.

Referência: Contar tokens antes de executar a inferência

Questão 10 de 12 · Domínio 5: Testes, validação e solução de problemas

Um job noturno em contêineres no Amazon ECS gera relatórios regulatórios longos chamando a Converse API do Amazon Bedrock com o boto3. Os relatórios pequenos funcionam, mas os maiores falham com ReadTimeoutError depois de cerca de um minuto, e o SDK repete a chamada sozinho, multiplicando o consumo de tokens sem concluir o relatório. As métricas do Bedrock não mostram throttling nem erros do serviço. Qual é a causa e a correção?

Resposta: D) O tempo de geração passa do timeout de leitura padrão do cliente do SDK; a correção é aumentar o read_timeout no Config do botocore e limitar os retries

Por quê: Clientes dos SDKs da AWS usam por padrão um timeout de leitura de cerca de um minuto, e gerações longas de LLM podem levar mais que isso. O cliente então desiste com ReadTimeoutError, e a política de retry repete a chamada, consumindo tokens de novo. A AWS recomenda aumentar o read_timeout do cliente (por exemplo, no Config do botocore) e ajustar as tentativas; para mostrar o texto ao usuário enquanto é gerado, a alternativa é o streaming.

Dica de prova: ReadTimeoutError após cerca de 60 s sem throttling: aumente o read_timeout do SDK e controle os retries.

Referência: Esquema da requisição e timeout do SDK (Amazon Nova)

Questão 11 de 12 · Domínio 1: Integração de modelos de base, gestão de dados e conformidade

Um escritório de advocacia indexa contratos em PDF numa base de conhecimento do Amazon Bedrock com chunking de tamanho fixo. Os chunks cortam cláusulas ao meio ou juntam o fim de uma cláusula com o início da seguinte, e perguntas como qual é a multa da cláusula 14 recebem respostas erradas. Os contratos seguem um padrão consistente de numeração de cláusulas. O escritório quer que cada chunk corresponda a uma cláusula inteira, com o número dela como metadado, mantendo a ingestão gerenciada pela base. Qual configuração atende a esses requisitos?

Resposta: C) Escolher a estratégia sem chunking e configurar uma Lambda de transformação customizada, com bucket intermediário no S3, que divide o texto por cláusula e grava o número dela como metadado do chunk

Por quê: As Knowledge Bases aceitam uma Lambda de transformação customizada na ingestão. Para chunking próprio, escolha a estratégia sem chunking e forneça a Lambda e um bucket intermediário no S3; a função lê o conteúdo, divide pela regra de negócio (por exemplo, por cláusula) e devolve arquivos com os chunks e metadados por chunk. A ingestão, os embeddings e a sincronização continuam gerenciados pela base.

Dica de prova: Divisão por estrutura de negócio (cláusula, artigo, item) que as estratégias nativas não respeitam: sem chunking + Lambda de transformação customizada.

Referência: Lambda de transformação customizada na ingestão

Questão 12 de 12 · Domínio 2: Implementação e integração

Uma rede de varejo tem um agente de atendimento escrito com Strands Agents. Três equipes mantêm servidores MCP próprios (estoque, pedidos e promoções) e publicam ferramentas novas quase toda semana. Hoje cada ferramenta é declarada no código do agente, e toda novidade exige novo deploy. A empresa quer que o agente passe a usar as ferramentas publicadas pelos servidores sem alterar o código dele a cada mudança. Qual solução atende a esses requisitos?

Resposta: C) Criar um MCPClient do Strands por servidor, listar as ferramentas com list_tools_sync no início de cada sessão e entregar a lista combinada ao agente, sem alterar o código dele

Por quê: No Model Context Protocol, o cliente pergunta ao servidor quais ferramentas ele oferece (tools/list) e recebe nome, descrição e esquema de entrada de cada uma. Com Strands Agents, um MCPClient por servidor e a chamada list_tools_sync entregam ao agente a lista atualizada a cada sessão. Assim, as equipes publicam ferramentas nos próprios servidores e o agente as usa sem mudança de código.

Dica de prova: Ferramentas que mudam com frequência e pertencem a outras equipes: descoberta dinâmica por cliente MCP, não declaração fixa no código.

Referência: Apresentação do Strands Agents (SDK de agentes)

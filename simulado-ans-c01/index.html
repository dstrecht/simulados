Questão 1 de 12Network Design

Um banco digital opera workloads em três VPCs na mesma região: VPC-App (aplicações), VPC-DB (bancos de dados) e VPC-Sec (ferramentas de segurança, como IDS/IPS e inspeção TLS). A empresa quer: • Centralizar a inspeção de tráfego L7 (TLS termination, IDS/IPS) em VPC-Sec para todo o tráfego Norte-Sul (Internet) e Leste-Oeste (entre VPCs); • Minimizar o uso de IPs privados adicionais e evitar crescimento explosivo de rotas em tabelas de roteamento; • Manter alta disponibilidade e caminho de retorno assimétrico sob controle; • Suportar crescimento futuro com novas VPCs na mesma região. Qual desenho de rede na AWS atende melhor a esses requisitos, considerando boas práticas avançadas de design?

✓ Resposta: C) Usar um Transit Gateway com VPC-App, VPC-DB e VPC-Sec e um Gateway Load Balancer na VPC-Sec, com tabelas de rotas passando o tráfego norte-sul e leste-oeste por ela

Por quê: Esta alternativa é a melhor arquitetura para centralizar inspeção em escala, mantendo simplicidade de rotas e suporte a crescimento. O AWS Transit Gateway (TGW) fornece um hub escalável para múltiplas VPCs, evitando full-mesh de peering e explosão de rotas. Ao integrar o TGW com AWS Gateway Load Balancer (GWLB) na VPC-Sec, é possível redirecionar tráfego (Norte-Sul e Leste-Oeste) para dispositivos virtuais de segurança (IDS/IPS, proxies, TLS inspection) de forma transparente e altamente disponível.

Dica de prova: Para inspeção centralizada em múltiplas VPCs na mesma região, pense em Transit Gateway + Gateway Load Balancer como o padrão de referência. Peering VPC é ótimo para cenários simples ponto a ponto, mas não escala bem para malhas complexas nem oferece trânsito.

Referência: Centralized inspection architecture with AWS Transit Gateway and Gateway Load Balancer

Questão 2 de 12Network Implementation

Uma equipe de redes precisa padronizar e automatizar a criação de topologias complexas entre contas, incluindo VPCs, anexos de AWS Transit Gateway, rotas e associações de tabelas de rota. O time deseja também aplicar boas práticas de segurança e governança de forma consistente, reduzindo erros manuais e permitindo reuso de modelos aprovados. Qual abordagem atende melhor a esses requisitos, considerando recursos nativos da AWS?

✓ Resposta: A) Utilizar AWS CloudFormation com AWS CloudFormation StackSets para definir e distribuir modelos de infraestrutura de rede entre contas e regiões, incluindo VPCs, anexos de Transit Gateway e rotas

Por quê: Esta alternativa é a melhor escolha porque o AWS CloudFormation, em conjunto com o CloudFormation StackSets, permite definir a infraestrutura de rede como código (IaC) e distribuí-la de forma centralizada e padronizada entre múltiplas contas e regiões. É possível modelar VPCs, sub-redes, anexos de AWS Transit Gateway, tabelas de rotas, associações e propagação de rotas em templates versionados, aplicando governança e boas práticas de segurança.

Dica de prova: Para ambientes multi-conta e multi-região, priorize sempre infraestrutura como código (CloudFormation, CDK, Terraform) e, dentro do ecossistema AWS, use StackSets quando precisar aplicar o mesmo padrão de rede em diversas contas.

Referência: AWS CloudFormation StackSets - Conceitos

Questão 3 de 12Network Management and Operation

Uma equipe de operações precisa monitorar a latência e a perda de pacotes entre uma aplicação em execução em instâncias Amazon EC2 em uma VPC no AWS e um ambiente on-premises conectado por AWS Site-to-Site VPN. Eles querem identificar rapidamente degradações de performance e visualizar métricas em um único painel, sem instalar agentes adicionais nas instâncias. Qual é a solução MAIS adequada e escalável para esse cenário?

✓ Resposta: B) Usar o CloudWatch Network Monitor com sondas entre a VPC e o on-premises, medindo latência e perda em dashboards do CloudWatch

Por quê: Esta alternativa é a mais adequada porque o AWS CloudWatch Network Monitor foi projetado especificamente para monitorar performance de rede (incluindo latência e perda de pacotes) entre recursos em VPCs e destinos externos, como ambientes on-premises conectados via VPN ou AWS Direct Connect.

Dica de prova: Quando a questão mencionar monitoramento de latência, perda de pacotes, caminho de rede e visibilidade ponta a ponta entre VPCs, on-premises ou Internet, sem agentes e com dashboards nativos, pense em AWS CloudWatch Network Monitor.

Referência: AWS CloudWatch Network Monitor

Questão 4 de 12Network Security, Compliance, and Governance

Uma empresa do setor financeiro possui dezenas de contas AWS organizadas via AWS Organizations. Por requisitos de conformidade, todo tráfego DNS de saída para a internet deve ser inspecionado centralmente, com bloqueio de domínios maliciosos e registro de consultas para auditoria. A empresa já utiliza AWS Firewall Manager para gerenciar políticas de AWS WAF e grupos de segurança em múltiplas contas. Qual é a abordagem MAIS adequada e escalável para atender esses requisitos de segurança e compliance de DNS?

✓ Resposta: A) Usar endpoints do Route 53 Resolver em uma conta central, regras de encaminhamento compartilhadas pelo RAM, DNS Firewall para filtragem e logs de consultas centralizados

Por quê: Esta alternativa é a mais adequada porque segue o padrão recomendado de arquitetura hub-and-spoke para DNS em ambientes multi-conta. Ao configurar endpoints inbound e outbound do Amazon Route 53 Resolver em uma conta central de rede, é possível: - Centralizar a inspeção e filtragem de DNS (por exemplo, usando Route 53 Resolver DNS Firewall ou uma solução de terceiros).

Dica de prova: Para ambientes multi-conta que exigem governança forte de DNS, pense em: (1) conta de rede central (hub), (2) Route 53 Resolver inbound/outbound endpoints, (3) compartilhamento de Resolver rules via AWS RAM, (4) DNS Firewall e Query Logging para compliance.

Referência: Arquiteturas de encaminhamento DNS com Amazon Route 53 Resolver

Questão 5 de 12Network Design

Uma empresa utiliza dezenas de VPCs em múltiplas contas AWS na mesma região e deseja um modelo de conectividade em malha parcial entre essas VPCs, com gerenciamento centralizado de roteamento e segurança. Os requisitos incluem: (1) minimizar a complexidade operacional de manter múltiplas conexões ponto a ponto; (2) permitir inspeção centralizada de tráfego leste-oeste (entre VPCs) em uma VPC de segurança; (3) evitar limites de escalabilidade comuns ao usar apenas VPC peering. Qual desenho atende melhor a esses requisitos?

✓ Resposta: C) Compartilhar um Transit Gateway pelo AWS RAM, anexar as VPCs e controlar o roteamento até a VPC de segurança pelas tabelas de rotas dele

Por quê: Esta alternativa usa o AWS Transit Gateway como plano de controle centralizado de roteamento, que é exatamente o serviço desenhado para interconectar múltiplas VPCs e redes on-premises em escala. Ao compartilhar o Transit Gateway via AWS Resource Access Manager (AWS RAM) entre contas, a empresa reduz a necessidade de manter dezenas de peerings individuais.

Dica de prova: Para cenários de múltiplas VPCs (10, 20, 100+), pense em AWS Transit Gateway como a opção padrão para malha controlada e escalável. VPC peering é adequado para poucos pares de VPCs ou casos simples; PrivateLink é para publicar serviços específicos (não como backbone de rede).

Questão 6 de 12Network Implementation

Uma empresa possui workloads em múltiplas VPCs na mesma Região AWS e quer implementar inspeção centralizada de tráfego L3/L4 e L7 usando um firewall de terceiros (appliance virtual) em uma VPC dedicada de segurança. Os requisitos são: - Evitar single point of failure, garantindo alta disponibilidade da inspeção. - Permitir escalabilidade horizontal dos appliances de firewall. - Manter a rota de retorno assimétrica sob controle, para que o tráfego de resposta também passe pelo firewall. - Reduzir a complexidade operacional, evitando o gerenciamento de centenas de rotas estáticas em cada VPC spoke. Qual abordagem atende melhor a esses requisitos?

✓ Resposta: D) Integrar o Transit Gateway a um Gateway Load Balancer na VPC de segurança, com o appliance como target e rotas do Transit Gateway forçando o tráfego por ele

Por quê: Esta alternativa é a mais adequada porque combina o AWS Transit Gateway (TGW) com o AWS Gateway Load Balancer (GWLB), que foi projetado exatamente para cenários de inspeção centralizada de tráfego com appliances de terceiros. O GWLB permite: - Escalabilidade horizontal: você registra múltiplos appliances como targets em um target group do GWLB, distribuindo o tráfego de forma balanceada.

Dica de prova: Para inspeção centralizada com appliances de terceiros em múltiplas VPCs, lembre-se da combinação Transit Gateway + Gateway Load Balancer.

Referência: Centralized inspection architecture with AWS Transit Gateway

Questão 7 de 12Network Management and Operation

Um time de operações precisa monitorar, em tempo quase real, a performance de centenas de túneis VPN de Site-to-Site e conexões AWS Direct Connect em múltiplas contas AWS, gerenciadas via AWS Organizations. O time quer: • Visualizar latência, perda de pacotes e status dos túneis VPN e links DX em um único painel centralizado. • Ser alertado automaticamente quando a latência ultrapassar um certo limiar ou quando um túnel ficar DOWN. • Minimizar a necessidade de scripts customizados em cada conta. Qual abordagem atende melhor a esses requisitos com a menor sobrecarga operacional?

✓ Resposta: D) Usar um painel com cross-account observability do CloudWatch reunindo métricas de VPN e Direct Connect, com alarmes em TunnelState e ConnectionState e alertas pelo SNS

Por quê: Esta alternativa é a mais adequada porque utiliza serviços nativos de observabilidade da AWS com suporte a múltiplas contas e regiões. As conexões VPN de Site-to-Site e o AWS Direct Connect já publicam métricas de estado e performance no Amazon CloudWatch (por exemplo, TunnelState, PacketLoss em CloudWatch Metrics ou via CloudWatch Logs, DxConnectionState, entre outras).

Dica de prova: Para provas avançadas da AWS, sempre que o requisito envolver monitoramento contínuo, métricas em tempo quase real e alertas automáticos, pense primeiro em Amazon CloudWatch (métricas, dashboards, alarms, cross-account observability) e Amazon SNS para notificação.

Referência: Monitoramento de VPN Site-to-Site com CloudWatch

Questão 8 de 12Network Security, Compliance, and Governance

A empresa ExampleCorp está migrando centenas de contas para uma organização AWS única e deseja aplicar um conjunto padronizado de políticas de segurança de rede (como regras de AWS WAF, grupos de segurança e listas de controle de acesso) de forma centralizada em todas as contas atuais e futuras. Além disso, a equipe de segurança precisa de visibilidade contínua sobre desvios de conformidade e a capacidade de corrigir automaticamente recursos que violem essas políticas. Qual serviço AWS é mais adequado para atender a esses requisitos?

✓ Resposta: B) AWS Firewall Manager

Por quê: O AWS Firewall Manager é um serviço de gerenciamento de segurança centralizado que permite configurar e gerenciar, de forma central, regras de firewall em múltiplas contas e recursos dentro de uma organização AWS. Ele foi projetado especificamente para cenários em que uma equipe de segurança central quer impor políticas padronizadas de segurança de rede e garantir conformidade contínua em todas as contas atuais e futuras da AWS Organizations.

Questão 9 de 12Network Design

Um Transit Gateway está associado a um Direct Connect gateway por transit VIF. Após anexar 30 VPCs novas (10.20.0.0/24 a 10.20.29.0/24), o data center não recebe rotas para elas. O time quer anunciar o mínimo de prefixos. O que fazer?

✓ Resposta: C) Incluir o resumo 10.20.0.0/16 nos allowed prefixes da associação entre o Direct Connect gateway e o Transit Gateway

Por quê: Com Transit Gateway e Direct Connect gateway, os prefixos anunciados ao on-premises são os allowed prefixes da associação, e não os CIDRs das VPCs automaticamente. Usar resumos reduz o número de rotas e evita estourar cotas de prefixos.

Dica de prova: On-premises sem rotas das VPCs pelo transit VIF: confira os allowed prefixes da associação DXGW-TGW.

Referência: Interações de allowed prefixes

Questão 10 de 12Network Implementation

Uma empresa está interligando duas VPCs em contas diferentes por meio de AWS Transit Gateway (TGW). As VPCs estão em regiões distintas (us-east-1 e eu-west-1). O time de rede precisa garantir que o tráfego entre as VPCs seja roteado pelo TGW, sem uso de VPC peering direto, e que novas VPCs possam ser adicionadas futuramente com o mínimo de reconfigurações. Qual abordagem de implementação atende melhor a esse requisito?

✓ Resposta: A) Usar um Transit Gateway em cada região com peering entre eles, cada VPC anexada ao da própria região e tabelas de rotas para a troca de tráfego

Por quê: Esta alternativa é a mais adequada porque segue o padrão recomendado de implementação multi-região com AWS Transit Gateway: um TGW por região, com peering entre Transit Gateways. Cada VPC é anexada ao TGW da sua própria região, o que simplifica a operação, reduz dependência de longas rotas cross-region em nível de VPC e permite adicionar novas VPCs apenas criando novos anexos e atualizando as tabelas de rotas do TGW.

Dica de prova: Para topologias multi-conta e multi-região, pense em AWS Transit Gateway como um hub regional. Use anexos de VPC para conectar os spokes e Transit Gateway peering para interligar hubs entre regiões.

Referência: Peering de AWS Transit Gateways

Questão 11 de 12Network Management and Operation

O time de operações precisa monitorar um AWS Transit Gateway que interliga dezenas de VPCs e VPNs: volume de bytes, pacotes descartados por falta de rota e alarmes para anomalias de tráfego. Qual abordagem é a mais adequada?

✓ Resposta: D) Usar as métricas nativas do Transit Gateway no CloudWatch, como BytesIn e PacketDropCountNoRoute, com dashboards e alarmes

Por quê: O Transit Gateway envia métricas ao CloudWatch em nível de gateway e de attachment, como BytesIn, BytesOut, PacketsIn, PacketDropCountBlackhole e PacketDropCountNoRoute. Com elas, criam-se dashboards e alarmes; para análise por fluxo, complemente com os Transit Gateway Flow Logs.

Dica de prova: Descarte de pacotes no Transit Gateway: métricas PacketDropCountBlackhole e PacketDropCountNoRoute no CloudWatch.

Referência: Documentação oficial

Questão 12 de 12Network Security, Compliance, and Governance

Uma equipe de segurança precisa garantir que todos os VPCs em múltiplas contas da AWS sigam padrões mínimos de segurança de rede, incluindo: (1) proibir security groups que permitam tráfego SSH (porta 22) irrestrito da internet, (2) impedir a criação de NACLs que permitam todo tráfego de entrada da internet, e (3) auditar continuamente recursos já existentes com alertas centralizados. Qual é a combinação de serviços e abordagem MAIS adequada para atender a esses requisitos com o menor esforço operacional?

✓ Resposta: B) Usar um agregador do AWS Config na conta de segurança, regras gerenciadas como restricted-ssh em todas as contas e o Security Hub centralizando os achados

Por quê: Esta alternativa é a mais adequada porque usa serviços nativos de governança e conformidade orientados a configuração, com escopo multi-conta e monitoramento contínuo. O AWS Config, integrado ao AWS Organizations, permite aplicar regras gerenciadas (por exemplo, para restringir SSH aberto e verificar NACLs) em todas as contas de forma centralizada. O Config Aggregator consolida a visão de conformidade em uma conta de segurança.

Dica de prova: Para governança multi-conta focada em segurança de rede (security groups, NACLs, VPCs), pense em: AWS Organizations + AWS Config (regras gerenciadas ou customizadas) + Config Aggregator + Security Hub.

Referência: AWS Config - Guia de Início

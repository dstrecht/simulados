Questão 1 de 12Desenvolvimento com os serviços da AWS

Um time de desenvolvimento está criando uma aplicação web que utilizará Amazon S3 para armazenar arquivos enviados pelos usuários. O time deseja reduzir o acoplamento entre a aplicação e o bucket S3, permitindo que a aplicação faça upload diretamente para o S3 sem que o backend precise receber os arquivos. Qual abordagem é a MAIS apropriada para atender a esse requisito?

✓ Resposta: B) Gerar URLs pré-assinadas (pre-signed URLs) no backend para que o cliente faça upload diretamente para o bucket S3

Por quê: Esta alternativa é a mais adequada porque o backend apenas gera URLs pré-assinadas (pre-signed URLs) com permissões e tempo de expiração controlados. O cliente faz o upload diretamente para o S3 usando essa URL, reduzindo o acoplamento e evitando que o backend faça o tráfego de dados, ao mesmo tempo em que mantém segurança e controle de acesso via IAM e políticas do bucket.

Dica de prova: Quando o enunciado falar em 'upload direto para o S3', 'reduzir acoplamento' e 'não trafegar o arquivo pelo backend', pense em URLs pré-assinadas (pre-signed URLs) como a solução padrão e recomendada pela AWS.

Questão 2 de 12Implantação

Uma equipe deseja automatizar a implantação de uma aplicação em containers no Amazon ECS (modo Fargate) sempre que um novo artefato de imagem Docker for enviado para o Amazon ECR. A equipe quer um fluxo totalmente gerenciado, com integrações nativas da AWS, suporte a aprovações manuais e possibilidade de adicionar etapas de testes automatizados no meio do processo. Qual solução atende melhor a esses requisitos com o menor esforço operacional?

✓ Resposta: C) Criar um pipeline usando AWS CodePipeline integrado ao Amazon ECR como origem, AWS CodeBuild para testes e AWS CodeDeploy para implantar no Amazon ECS

Por quê: Esta alternativa é a melhor escolha porque utiliza o AWS CodePipeline como orquestrador central, com origem no Amazon ECR (imagem Docker), etapas de build/teste no AWS CodeBuild e implantação no Amazon ECS via AWS CodeDeploy. O CodePipeline é totalmente gerenciado, suporta facilmente aprovações manuais, integrações nativas com serviços da AWS e permite adicionar estágios de teste automatizados entre o build e o deploy com baixo esforço operacional.

Dica de prova: Em questões de prova, quando os requisitos envolvem: (1) pipeline de CI/CD gerenciado, (2) integrações nativas com serviços AWS, (3) aprovações manuais e (4) facilidade para adicionar testes, o serviço padrão a ser lembrado é o AWS CodePipeline, geralmente combinado com CodeBuild (build/testes) e CodeDeploy (deploy em ECS, EC2 ou Lambda).

Questão 3 de 12Segurança

Uma startup de saúde construiu uma API de prontuário médico no Amazon ECS (Fargate), exposta por meio de um Application Load Balancer (ALB). A API precisa autenticar usuários finais usando OAuth 2.0/OpenID Connect e garantir que apenas clientes autorizados consigam invocar os endpoints, sem que a aplicação tenha que validar tokens manualmente. O time também quer evitar gerenciar servidores de autenticação próprios. Qual abordagem atende melhor aos requisitos, seguindo boas práticas de segurança na AWS?

✓ Resposta: D) Usar autenticação OIDC no listener do ALB com Cognito ou outro IdP, exigida antes de encaminhar ao target group

Por quê: Esta alternativa é a mais adequada porque utiliza o suporte nativo do Application Load Balancer à autenticação OIDC/OAuth 2.0. Nesse modelo, o ALB redireciona o usuário para o provedor de identidade (por exemplo, Amazon Cognito, Auth0, Okta), recebe o token de volta e só encaminha a requisição ao serviço no ECS após autenticação bem-sucedida.

Dica de prova: Quando a pergunta envolver autenticação de usuários web ou mobile para aplicações atrás de ALB, procure por 'ALB + OIDC/OAuth2 + Amazon Cognito/IdP externo'.

Referência: Autenticação de usuários com Application Load Balancer (OIDC)

Questão 4 de 12Troubleshooting e Otimização

Durante um teste de carga em um ambiente de staging, uma aplicação serverless em AWS Lambda escrita em Node.js apresenta aumento súbito de latência e esporádicos erros 5xx. As funções são invocadas por uma API HTTP do Amazon API Gateway. Você precisa identificar rapidamente o gargalo e otimizar o desempenho, minimizando o esforço operacional. Qual é a abordagem MAIS adequada e alinhada com boas práticas da AWS?

✓ Resposta: C) Ativar o AWS X-Ray para a API Gateway e para as funções Lambda, configurar anotações e subsegmentos na aplicação, e usar o Service Map para identificar exatamente onde ocorrem as maiores latências (rede, Lambda, downstream) e otimizar os trechos de código mais lentos.

Por quê: Esta alternativa é a melhor abordagem porque o AWS X-Ray fornece rastreamento distribuído de ponta a ponta entre API Gateway, Lambda e serviços downstream (como DynamoDB, SQS, RDS, etc.). Ao instrumentar a aplicação com anotações e subsegmentos, você consegue visualizar exatamente onde está o tempo gasto (cold start, execução de código, chamadas externas) e qual componente está gerando erros 5xx.

Dica de prova: Para troubleshooting e otimização em arquiteturas serverless, combine CloudWatch Logs/Metrics com AWS X-Ray. Use o Service Map para ter visão global dos serviços e, em seguida, aprofunde nos traces individuais para encontrar funções lentas, cold starts e chamadas externas com alta latência.

Questão 5 de 12Desenvolvimento com os serviços da AWS

Uma API REST está exposta no Amazon API Gateway (HTTP API) e integrada a funções AWS Lambda. Em ambiente de produção, picos de tráfego ocasionais estão gerando aumento significativo de latência e erros 429 em alguns clientes, mesmo sem atingir o limite de concorrência das funções Lambda. O desenvolvedor precisa reduzir a latência percebida e proteger a API contra estouros de carga súbitos, garantindo também que clientes importantes tenham maior chance de sucesso em momentos de pico. Qual é a solução MAIS adequada, com o menor esforço operacional, considerando boas práticas de desenvolvimento serverless na AWS?

✓ Resposta: A) Usar Throttling no API Gateway com limites globais e usage plans com API keys definindo cotas e burst por grupo de clientes

Por quê: Esta alternativa é a mais adequada porque usa recursos nativos do API Gateway para controlar tráfego de forma granular. O throttling em nível de API (RPS e burst) suaviza picos, reduz erros 429 na borda e protege o backend.

Dica de prova: Para APIs serverless, comece sempre explorando o que o API Gateway já oferece: throttling (RPS/burst), usage plans, API keys e, se necessário, caching seletivo.

Questão 6 de 12Implantação

Uma empresa está migrando um monólito para microsserviços em containers. Cada microsserviço será empacotado como imagem Docker armazenada no Amazon ECR e executado em tarefas do Amazon ECS em modo Fargate. Os desenvolvedores querem um fluxo totalmente automatizado que: (1) faça build da imagem e rode testes unitários; (2) armazene a imagem versionada; (3) faça implantação blue/green com possibilidade de rollback automático em caso de falha de saúde da nova versão, sem tempo de inatividade. Qual combinação de serviços e configurações atende a esses requisitos com o mínimo de esforço operacional contínuo?

✓ Resposta: A) Usar AWS CodeCommit como repositório de código, CodeBuild para build e testes, CodePipeline para orquestrar o fluxo e AWS CodeDeploy com tipo de implantação ECS blue/green integrado a um Application Load Balancer, configurando validação de saúde e rollback automático.

Por quê: Esta alternativa descreve o padrão recomendado e totalmente gerenciado para CI/CD de aplicações em ECS Fargate com zero downtime e rollback automático.

Dica de prova: Para ECS (especialmente com Fargate), memorize que rollback automático + blue/green + verificação de saúde via ALB geralmente envolve: CodePipeline + CodeBuild + ECR + CodeDeploy (deployment type: ECS).

Questão 7 de 12Segurança

Uma API REST crítica está exposta por meio de um Application Load Balancer (ALB) em uma VPC pública. O time de segurança determinou que todo o tráfego entre os clientes e o ALB, bem como entre o ALB e as instâncias EC2 no backend, deve ser criptografado usando TLS. Como um desenvolvedor deve configurar a solução para atender a esse requisito com o mínimo de esforço operacional e mantendo boas práticas de segurança?

✓ Resposta: B) Configurar o ALB com um listener HTTPS (porta 443) usando um certificado do AWS Certificate Manager (ACM) e configurar o target group para usar a porta 443 nas instâncias EC2, que terão certificados autoassinados gerenciados manualmente pelo time de desenvolvimento.

Por quê: Esta alternativa é a mais adequada porque garante criptografia ponta a ponta: cliente -> ALB e ALB -> instâncias EC2, atendendo ao requisito de que todo o tráfego seja criptografado. O ALB usa um certificado gerenciado pelo ACM na borda (listener HTTPS), o que reduz o esforço operacional para renovação e rotação do certificado público. No backend, o target group usa porta 443 e as instâncias EC2 expõem HTTPS.

Dica de prova: Em provas da AWS, quando o enunciado fala explicitamente em criptografar 'todo o tráfego' ou 'de ponta a ponta', pense em TLS em todas as arestas: cliente -> load balancer e load balancer -> backend.

Referência: Configurar listeners HTTPS no Application Load Balancer

Questão 8 de 12Troubleshooting e Otimização

Um aplicativo de processamento de pedidos usa uma função AWS Lambda escrita em Python, acionada por eventos do Amazon SQS. Em horários de pico, as mensagens começam a acumular na fila e o tempo de processamento total aumenta bastante. O CloudWatch Logs mostra que a função Lambda frequentemente atinge o limite de tempo (timeout) ao chamar uma API externa de pagamento, e as métricas indicam aumento de erros e retries. O desenvolvedor precisa otimizar a solução para reduzir o acúmulo de mensagens e os timeouts, mantendo custos sob controle. Qual é a MELHOR abordagem?

✓ Resposta: A) Usar Timeout e backoff nas chamadas à API, timeout menor na função, visibility timeout da fila acima dele e concorrência controlada

Por quê: Esta alternativa é a melhor solução por abordar o problema de forma completa e orientada a boas práticas. Ao implementar timeout e retries com backoff exponencial na chamada à API externa, a função passa a lidar melhor com instabilidades do serviço de terceiros, evitando waits longos desnecessários. Reduzir o timeout da função Lambda faz com que falhas ocorram mais rapidamente (fail fast), liberando recursos e evitando que a função fique presa em chamadas muito longas.

Dica de prova: SQS + Lambda exige alinhamento entre 'visibility timeout' da fila e timeout da função. 'visibility timeout' deve ser sempre MAIOR que o timeout da Lambda para evitar processamento duplicado.

Questão 9 de 12Desenvolvimento com os serviços da AWS

Uma startup está desenvolvendo um backend serverless em AWS Lambda integrado com Amazon API Gateway. Em ambiente de produção, algumas requisições HTTP retornam erro 429 (Too Many Requests) no API Gateway, mesmo com a Lambda apresentando baixa utilização de CPU e memória nos logs do CloudWatch. O time quer minimizar esses erros sem superdimensionar desnecessariamente os recursos. Qual abordagem é MAIS adequada para lidar com esse cenário?

✓ Resposta: A) Usar Throttling por estágio no API Gateway com limites de burst e rate, e retry exponencial no cliente ao receber 429

Por quê: Esta alternativa é a mais adequada porque o erro 429 no Amazon API Gateway está relacionado a limites de taxa (rate) e rajada (burst) de requisições, não necessariamente ao consumo de CPU/memória da função Lambda. Ao configurar o throttling em nível de estágio ou de método, você controla explicitamente quantas requisições por segundo são permitidas e como o sistema reage a picos.

Dica de prova: Erros 429 em API Gateway normalmente indicam limitação de taxa (throttling), não problemas de CPU/memória da Lambda. Sempre verifique e ajuste as configurações de rate/burst no estágio/método do API Gateway e considere implementar backoff exponencial no cliente quando receber 429.

Questão 10 de 12Implantação

Você está versionando funções AWS Lambda usando AWS SAM e precisa implantar uma nova versão em produção com o mínimo de downtime possível, permitindo rollback rápido caso ocorra algum problema. Além disso, você quer que apenas uma parte do tráfego seja roteada inicialmente para a nova versão, aumentando gradualmente conforme a confiança. Qual abordagem de implantação atende melhor a esses requisitos?

✓ Resposta: C) Usar Alias prod apontando para versões da função e DeploymentPreference Linear ou Canary no template SAM

Por quê: Esta alternativa é a correta porque usa o padrão recomendado pela AWS para deployments controlados de Lambda com AWS SAM: utilizar aliases (por exemplo, 'prod') apontando para versões imutáveis da função e configurar 'deploymentPreference' no template SAM (como 'Canary10Percent5Minutes' ou 'Linear10PercentEvery1Minute').

Dica de prova: Para Lambda + SAM, grave: alias = ponte para produção. Sempre que precisar de canary/blue-green/linear deployment e rollback rápido, pense em: versão imutável + alias + 'deploymentPreference' no SAM (ou CodeDeploy). Isso evita alterar diretamente '$LATEST' e facilita auditoria, teste e reversão.

Questão 11 de 12Segurança

Uma equipe precisa garantir que apenas funções AWS Lambda específicas possam descriptografar segredos armazenados em um bucket Amazon S3 usando AWS KMS. Qual abordagem é mais adequada para atender a esse requisito de segurança com o menor esforço operacional?

✓ Resposta: B) Criar uma CMK no AWS KMS, usar essa chave para criptografar os segredos e definir uma key policy que permita o uso da chave apenas para as funções Lambda específicas

Por quê: Esta alternativa é a mais adequada porque utiliza uma chave gerenciada pelo cliente (CMK) no AWS KMS com uma key policy bem definida. Essa key policy pode restringir explicitamente o uso da chave apenas às funções Lambda desejadas, garantindo que somente essas funções possam chamar as operações de decrypt no KMS. Além disso, o uso de KMS integrado ao S3 reduz o esforço operacional, pois a criptografia e descriptografia são gerenciadas de forma transparente pelos serviços da AWS.

Dica de prova: Quando precisar restringir quem pode descriptografar dados criptografados com KMS, pense sempre em duas camadas: (1) key policy da CMK (quem pode usar a chave) e (2) IAM role da função (quem pode assumir o papel e chamar o KMS). Use CMKs para granularidade de acesso mais fina do que SSE-S3 padrão.

Referência: AWS KMS Key Policies

Questão 12 de 12Troubleshooting e Otimização

Um sistema de processamento de pedidos em produção, executando em instâncias Amazon EC2 por trás de um Application Load Balancer (ALB), está apresentando aumento de latência e alguns erros 5xx intermitentes durante picos de tráfego. As métricas do Amazon CloudWatch mostram que a CPU das instâncias EC2 está constantemente abaixo de 40%, mas a métrica TargetResponseTime do ALB aumenta significativamente nesses períodos. O desenvolvedor também observa, nos logs de acesso do ALB e nos logs da aplicação, vários erros relacionados a conexões com o banco de dados Amazon RDS. Qual abordagem é mais adequada para diagnosticar e otimizar essa aplicação com o menor impacto em produção?

✓ Resposta: A) Ativar o AWS X-Ray na aplicação, instrumentando as chamadas ao banco de dados e endpoints críticos, e usar amostragem para rastrear as requisições de alta latência e identificar gargalos específicos nas queries ou no código.

Por quê: Esta alternativa é a mais adequada porque o AWS X-Ray foi projetado justamente para rastrear requisições de ponta a ponta, permitindo visualizar onde está o gargalo (aplicação, chamadas externas, banco de dados, etc.). Ao instrumentar as chamadas ao Amazon RDS e endpoints críticos, o desenvolvedor consegue correlacionar picos de latência com queries específicas, problemas de conexão ou trechos de código ineficientes.

Dica de prova: Quando a CPU das instâncias está baixa, mas a latência e os erros aumentam, desconfie de dependências externas (banco de dados, serviços de terceiros) e de problemas de conexão ou lock em recursos.

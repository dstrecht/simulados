Resumo por domínio e pegadinhas da GitHub Foundations GH-900

Como a prova pensa

A GH-900 é uma prova de fundamentos: cada enunciado descreve uma necessidade concreta e pede o comando, o recurso, o arquivo ou a configuração exata que a resolve. As alternativas erradas quase sempre são recursos reais do GitHub ou comandos reais do Git com outra função, então ganhar a prova é saber o propósito preciso de cada um, não apenas reconhecer o nome. Aparecem também itens de múltipla resposta (escolha duas) e pares que se invertem na alternativa errada, como fetch e pull ou fork e clone. Detalhes de restrição no enunciado (sem reescrever o histórico, mantendo as alterações, sem ser membro, sem escrever código) definem a resposta. Fundamentos de Git e GitHub responde por 25–30% e é onde a prova mais pontua.

Fundamentos de Git e GitHub (25–30% da prova)

  • Armadilha: Achar que git fetch já atualiza a main local (ou que pull só baixa). Como evitar: fetch só baixa e atualiza origin/main; a main local só muda após o merge. pull = fetch + integração.
  • Armadilha: Escolher git reset --hard com push forçado para desfazer um commit que já está na main compartilhada. Como evitar: Isso reescreve o histórico compartilhado. Em branch compartilhado, a resposta é git revert, que cria um commit novo.
  • Gatilho: se o enunciado traz “trocar de branch com urgência sem comitar o trabalho pela metade”, pense em: git stash (depois git stash pop).
  • Gatilho: se o enunciado traz “commit perdido depois de git reset --hard”, pense em: git reflog para achar o hash.

Repositórios do GitHub (10–15% da prova)

  • Armadilha: Escolher CODE_OF_CONDUCT.md para orientar padrões de código e envio de mudanças. Como evitar: Código de conduta é convivência; processo técnico de contribuição é CONTRIBUTING.md.
  • Armadilha: Achar que repositório público sem LICENSE é de domínio público ou recebe MIT automaticamente. Como evitar: Sem licença valem os direitos autorais padrão; nada é permitido explicitamente e o GitHub não escolhe licença.
  • Gatilho: se o enunciado traz “chamar automaticamente revisores para mudanças em uma pasta”, pense em: CODEOWNERS.
  • Gatilho: se o enunciado traz “regras de convivência”, pense em: CODE_OF_CONDUCT.md.

Colaboração no GitHub (10–15% da prova)

  • Armadilha: Escolher Rebase and merge para juntar todos os commits em um só. Como evitar: Rebase and merge aplica cada commit; quem junta é Squash and merge.
  • Armadilha: Escolher Squash and merge para preservar todos os commits. Como evitar: Squash junta tudo. Preservar e registrar a integração com commit extra = Create a merge commit.
  • Gatilho: se o enunciado traz “um commit só no branch de destino”, pense em: Squash and merge.
  • Gatilho: se o enunciado traz “cada commit no destino, sem commit de merge”, pense em: Rebase and merge.

Práticas Modernas de Desenvolvimento (10–15% da prova)

  • Armadilha: Usar uses: test, env: test ou runs-on: test para o deploy esperar o test. Como evitar: uses chama actions, env define variáveis e runs-on define o executor. Ordem entre jobs = needs.
  • Armadilha: Escolher repository_dispatch para execução manual pela interface. Como evitar: repository_dispatch é por API. Botão manual na interface = workflow_dispatch.
  • Gatilho: se o enunciado traz “job deploy só depois do job test”, pense em: needs: test.
  • Gatilho: se o enunciado traz “rodar todo dia em um horário, sem depender de commits”, pense em: schedule com cron (UTC).

Gerenciamento de Projetos no GitHub (5–10% da prova)

  • Armadilha: Usar um rótulo de versão para acompanhar entrega com prazo e progresso. Como evitar: Rótulo só classifica. Prazo e barra de progresso = milestone.
  • Armadilha: Escolher Roadmap ou Board para a visão de planilha. Como evitar: Roadmap é linha do tempo e Board é colunas. Planilha = Table.
  • Gatilho: se o enunciado traz “sprints”, pense em: Campo de iteração.
  • Gatilho: se o enunciado traz “prioridade Alta, Média ou Baixa”, pense em: Campo de seleção única.

Privacidade, Segurança e Administração (10–15% da prova)

  • Armadilha: Escolher secret scanning para bloquear o token antes do push. Como evitar: Secret scanning detecta; quem bloqueia antes é a proteção de push.
  • Armadilha: Escolher Dependabot ou secret scanning para analisar vulnerabilidades no código com CodeQL. Como evitar: Dependabot trata de dependências e secret scanning de credenciais. Código-fonte = code scanning.
  • Gatilho: se o enunciado traz “bloquear token antes de chegar ao repositório”, pense em: Proteção de push.
  • Gatilho: se o enunciado traz “token de API enviado por engano em commit”, pense em: Varredura de segredos (e revogar o token).

Comunidade do GitHub (5–10% da prova)

  • Armadilha: Achar que dar estrela gera notificações ou cria um fork. Como evitar: Estrela é favorito e apreço; notificações vêm do Watch e cópia é o fork.
  • Armadilha: Achar que Watch dá acesso de escrita ao código. Como evitar: Watch só gera notificações; nem estrela nem Watch dão acesso.
  • Gatilho: se o enunciado traz “contribuir sem permissão de escrita”, pense em: Fork, alterar e abrir um PR.
  • Gatilho: se o enunciado traz “fork desatualizado em relação ao original”, pense em: Sync fork.

Erros que mais custam pontos

  • Marcar um recurso real de outra finalidade só porque o nome parece familiar (Pulse em vez de Traffic, CODE_OF_CONDUCT em vez de CONTRIBUTING).
  • Ignorar se o commit já foi compartilhado e escolher reset --hard com push forçado em vez de revert.
  • Confundir detectar com prevenir em segurança: secret scanning em vez de push protection.
  • Inverter pares de conceitos (fetch e pull, fork e clone, base e compare, Enterprise Cloud e Server).

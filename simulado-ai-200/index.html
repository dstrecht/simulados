Resumo por domínio e pegadinhas da Azure AI Cloud Developer AI-200

Como a prova pensa

O AI-200 (Developing AI Cloud Solutions on Azure) substituiu o AZ-204, aposentado em 31/07/2026, e é uma prova de desenvolvedor: quase todo enunciado descreve um requisito curto e pede a configuração, função, política ou comando exato. As restrições do enunciado decidem tudo: sem chave, menor privilégio, sem alterar o código, sem nova implantação, sem gerenciar servidor ou cluster, em segundos, menor custo. As alternativas erradas costumam ser recursos reais do Azure que resolvem outro problema, como aumentar réplicas, trocar região, subir a temperatura ou olhar o log de atividades. A Microsoft favorece identidade gerenciada com RBAC no menor escopo, Key Vault para segredos e recursos gerenciados no lugar de código próprio. O formato tem múltipla escolha e múltipla resposta; nas de múltipla resposta, o enunciado diz quantas opções marcar, como 'Escolha DUAS'.

Desenvolver soluções em contêineres no Azure (20-25% da prova)

  • Armadilha: Escalar por requisições simultâneas com uma regra de CPU com limite de 50%. Como evitar: CPU não mede requisições simultâneas. Use a regra HTTP com concurrentRequests no valor pedido.
  • Armadilha: Fixar réplicas mínimas em três para ter três réplicas em horário comercial. Como evitar: Mínimo fixo mantém as réplicas sempre ligadas, inclusive fora do horário. Escala por horário é o escalonador cron do KEDA.
  • Gatilho: se o enunciado traz “descoberta de serviço, mTLS e repetições sem escrever esse código”, pense em: Dapr com a API de invocação de serviço.
  • Gatilho: se o enunciado traz “agente de mensagens trocável sem alterar o código”, pense em: Componente de pub/sub do Dapr.

Desenvolver soluções de IA com serviços de dados do Azure (25-30% da prova)

  • Armadilha: Aumentar a temperatura para trazer conhecimento, melhorar a busca, corrigir formato ou caber no contexto. Como evitar: Temperatura só muda a variação. Para consistência, ela deve ser baixa; para os demais problemas, procure a técnica específica.
  • Armadilha: Colocar todos os documentos na mensagem de sistema. Como evitar: Isso estoura o limite de contexto. Use RAG e envie só os trechos relevantes.
  • Gatilho: se o enunciado traz “documentos internos que mudam toda semana, sem treinar o modelo”, pense em: RAG.
  • Gatilho: se o enunciado traz “combinar palavras-chave e similaridade vetorial e reordenar por relevância”, pense em: Busca híbrida com classificador semântico.

Conectar e consumir serviços do Azure (20-25% da prova)

  • Armadilha: Usar ReceiveAndDelete com leitura rápida para não perder mensagens. Como evitar: A mensagem é removida ao ser lida e se perde na falha. Use PeekLock e conclua após processar.
  • Armadilha: Receber com PeekLock só para inspecionar mensagens. Como evitar: PeekLock bloqueia a mensagem. Para inspecionar sem remover nem bloquear, use peek.
  • Gatilho: se o enunciado traz “eventos discretos, por push, para vários assinantes com filtros”, pense em: Azure Event Grid.
  • Gatilho: se o enunciado traz “entrega confiável, fila de mensagens mortas e transações”, pense em: Azure Service Bus.

Proteger, monitorar e solucionar problemas de soluções do Azure (20-25% da prova)

  • Armadilha: Escolher identidade atribuída pelo sistema quando a permissão no Key Vault precisa existir antes do app. Como evitar: Ela só existe depois que o app é criado. Use identidade atribuída pelo usuário.
  • Armadilha: Usar políticas de acesso do cofre em um Key Vault novo. Como evitar: É o modelo legado. O recomendado é Azure RBAC.
  • Gatilho: se o enunciado traz “permissões precisam existir antes da criação do app”, pense em: Identidade atribuída pelo usuário.
  • Gatilho: se o enunciado traz “app com várias identidades autentica com a errada”, pense em: Informar o client ID.

Erros que mais custam pontos

  • Escolher uma função de plano de controle para acessar dados ou chamar o modelo: Leitor resulta em 403; Colaborador e Proprietário dão mais acesso que o necessário e ferem o menor privilégio.
  • Confundir sonda de prontidão com sonda de atividade, ou réplicas mínimas fixas com regra de escala.
  • Achar que guardar chaves no Key Vault ou rotacioná-las impede o uso de chaves, quando o certo é desativar a autenticação local.
  • Trocar o modelo de embeddings só nas consultas ou responder problemas de RAG com temperatura em vez de ajustar a recuperação.

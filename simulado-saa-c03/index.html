Questão 1 de 12 · Domínio 1: Criação de arquiteturas seguras

Uma companhia de seguros precisa expor uma API REST na AWS para parceiros externos. Os requisitos incluem: (1) autenticação forte para consumidores da API, (2) validação de escopo e chaves de acesso rotacionáveis, (3) capacidade de aplicar políticas de uso por cliente (rate limiting) e (4) evitar expor diretamente as credenciais de IAM da conta. Qual é a solução MAIS adequada e alinhada às boas práticas de segurança da AWS?

Resposta: C) Configurar o Amazon API Gateway com um authorizer do Amazon Cognito user pool para os parceiros, validando tokens JWT e escopos, e aplicar usage plans com chaves de API por cliente

Por quê: O Amazon API Gateway valida, com um authorizer do Amazon Cognito, os tokens JWT emitidos por um user pool em que cada parceiro é um cliente de aplicação, e pode exigir escopos OAuth por método. Os tokens expiram e são renovados, então nenhuma credencial IAM é exposta. Para limitar o uso por cliente, usage plans associados a chaves de API aplicam throttling e cotas; a chave de API identifica o cliente, mas não substitui a autenticação feita pelo Cognito.

Dica de prova: API para parceiros externos: API Gateway + authorizer do Cognito (JWT e escopos) para autenticar e usage plans com chaves de API para limitar por cliente. Chave de API sozinha não é autenticação.

Referência: Usage plans e chaves de API no API Gateway

Questão 2 de 12 · Domínio 2: Criação de arquiteturas resilientes

Uma loja on-line envia uma mensagem para uma fila Amazon SQS padrão a cada pedido, e um worker captura o pagamento e emite a nota fiscal. O provedor de pagamentos leva cerca de 5 minutos para concluir a análise antifraude depois da compra, e capturas tentadas antes disso falham e geram retentativas. A empresa quer que todas as mensagens novas fiquem 5 minutos invisíveis aos consumidores antes do primeiro processamento, sem alterar o código dos produtores nem do worker. Qual solução atende a esses requisitos?

Resposta: A) Configurar a fila como delay queue, definindo o atributo DelaySeconds da fila em 300 segundos para que cada mensagem nova espere 5 minutos

Por quê: O SQS tem dois mecanismos para esconder mensagens: delay queue ou message timer (DelaySeconds), que oculta a mensagem logo após o envio, por até 15 minutos, e visibility timeout, que oculta a mensagem depois que um consumidor a recebe, para evitar processamento duplicado. Para atrasos maiores que 15 minutos, a AWS indica o EventBridge Scheduler.

Dica de prova: Adiar o primeiro processamento por até 15 min = delay queue/DelaySeconds. Esconder enquanto alguém processa = visibility timeout.

Referência: Delay queues do Amazon SQS

Questão 3 de 12 · Domínio 3: Criação de arquiteturas de alto desempenho

Instâncias EC2 em três zonas de disponibilidade precisam gravar e ler os mesmos arquivos, e o armazenamento deve continuar disponível se uma zona falhar. Qual serviço atende a esse requisito?

Resposta: D) Amazon EFS (classe Standard, regional)

Por quê: O Amazon EFS na classe Standard armazena os dados de forma redundante em várias zonas de disponibilidade e pode ser montado ao mesmo tempo por instâncias em todas elas. O EBS Multi-Attach funciona dentro de uma única zona e só para volumes io1 e io2, o armazenamento de instância é temporário e snapshots não oferecem acesso compartilhado contínuo.

Dica de prova: Arquivos compartilhados entre zonas de disponibilidade: Amazon EFS.

Referência: O que é o Amazon EFS

Questão 4 de 12 · Domínio 4: Criação de arquiteturas com custo otimizado

Uma empresa publica um grande conjunto de dados no S3 para pesquisadores de outras organizações e quer que eles paguem pelas transferências de dados e requisições que fizerem. Qual recurso deve usar?

Resposta: C) S3 Requester Pays

Por quê: Com o Requester Pays ativado no bucket, quem faz a requisição paga pelas requisições e pela transferência de dados, enquanto o dono continua pagando pelo armazenamento. Os solicitantes precisam estar autenticados na AWS. O Transfer Acceleration acelera uploads, o Intelligent-Tiering otimiza o armazenamento e o Object Lock impede exclusões.

Dica de prova: Quem baixa paga: S3 Requester Pays.

Questão 5 de 12 · Domínio 1: Criação de arquiteturas seguras

Uma organização do setor financeiro precisa disponibilizar um endpoint de API altamente seguro para clientes externos. Os requisitos incluem: (1) proteção contra ataques de injeção e XSS; (2) validação de formato e tamanho de payload JSON; (3) limitação de taxa diferenciada por tipo de cliente (premium e padrão); (4) possibilidade de bloquear rapidamente origens suspeitas sem alterar o código da aplicação; e (5) terminação TLS obrigatória com suporte a inspeção detalhada. A API é exposta via Amazon API Gateway e integrada a funções AWS Lambda em sub-redes privadas. Qual combinação de soluções atende melhor a esses requisitos com o menor esforço operacional contínuo?

Resposta: A) WAF com regras gerenciadas, rate-based e IP sets no API Gateway, validação de requisição por modelo JSON e usage plans por tipo de cliente

Por quê: Cada requisito tem um recurso gerenciado. O AWS WAF, associado ao estágio do API Gateway (ou ao CloudFront à frente dele), bloqueia injeção e XSS com regras gerenciadas, limita abusos com rate-based rules e bloqueia origens suspeitas atualizando um IP set, sem alterar a aplicação. No API Gateway, o request validator compara o corpo com um modelo JSON Schema, e usage plans com chaves de API aplicam throttling e cotas diferentes para clientes premium e padrão. O TLS termina no API Gateway, onde a requisição é inspecionada.

Dica de prova: API pública protegida: WAF (regras gerenciadas, rate-based, IP sets) no API Gateway ou no CloudFront, request validation com modelo e usage plans para limites por cliente.

Referência: AWS WAF para APIs REST do API Gateway

Questão 6 de 12 · Domínio 2: Criação de arquiteturas resilientes

Uma aplicação pode ficar algumas horas fora do ar em um desastre regional, mas o banco de dados precisa estar continuamente replicado. A empresa quer o menor custo possível na região de recuperação. Qual estratégia de DR é a mais indicada?

Resposta: D) Pilot light com o banco replicado

Por quê: No pilot light, os dados ficam replicados continuamente na região de recuperação, mas a camada de aplicação fica desligada ou mínima e só é provisionada no desastre, o que resulta em RTO de dezenas de minutos a horas e custo baixo. Warm standby e multi-site mantêm capacidade ativa e custam mais, e backup e restauração não manteria o banco replicado.

Dica de prova: Dados replicados e aplicação desligada até o desastre: pilot light.

Referência: Opções de recuperação de desastres na AWS

Questão 7 de 12 · Domínio 3: Criação de arquiteturas de alto desempenho

Uma empresa de logística global executa uma aplicação de rastreamento de entregas em múltiplas Regiões da AWS. A aplicação é composta por instâncias Amazon EC2 em um Auto Scaling group atrás de um Application Load Balancer (ALB). Os usuários relatam alta latência ao acessar a aplicação a partir de diferentes continentes. O arquiteto de soluções precisa projetar uma solução que reduza a latência para usuários globais, mantenha alta disponibilidade e minimize o impacto de falhas regionais, sem exigir grandes mudanças na aplicação. Qual abordagem atende melhor a esses requisitos?

Resposta: A) Utilizar AWS Global Accelerator com endpoints nos ALBs em múltiplas Regiões e health checks, permitindo failover automático entre Regiões e roteamento via rede global da AWS para reduzir a latência.

Por quê: O AWS Global Accelerator fornece dois endereços IP anycast estáticos e leva o tráfego do usuário para a rede global da AWS no ponto de presença mais próximo. Endpoint groups em cada Região apontam para os ALBs já existentes, e os health checks do serviço direcionam cada usuário para a Região saudável mais próxima, com failover rápido e sem mudar a aplicação. O CloudFront é mais indicado para conteúdo cacheável, e o roteamento por geolocalização do Route 53 não escolhe pela latência e depende do cache de DNS para mudar de destino.

Dica de prova: Aplicação dinâmica multi-Região com menor latência e failover rápido: Global Accelerator com endpoint groups por Região. Conteúdo cacheável: CloudFront.

Referência: O que é o AWS Global Accelerator

Questão 8 de 12 · Domínio 4: Criação de arquiteturas com custo otimizado

Uma equipe de TI precisa reduzir custos de armazenamento de backups em longo prazo no Amazon S3. Os dados são acessados apenas em caso de auditorias, que ocorrem raramente, mas quando isso acontece é aceitável aguardar várias horas para recuperar os arquivos. Atualmente, todos os backups estão em S3 Standard. Qual é a opção MAIS econômica e alinhada a esse perfil de acesso?

Resposta: A) Usar regras de Lifecycle para mover backups antigos ao S3 Glacier Deep Archive

Por quê: O S3 Glacier Deep Archive tem o menor custo de armazenamento do S3 e é feito para dados raramente acessados que toleram recuperação em horas (até 12 horas na recuperação padrão). Uma regra de lifecycle move os backups do Standard para essa classe automaticamente. Glacier Instant Retrieval e Intelligent-Tiering custam mais por GB quando o dado é claramente frio, e EBS é armazenamento em bloco mais caro.

Dica de prova: Arquivo raro, recuperação em horas aceitável, menor custo: lifecycle para S3 Glacier Deep Archive.

Referência: Classes de armazenamento do Amazon S3

Questão 9 de 12 · Domínio 1: Criação de arquiteturas seguras

Uma fintech usa o AWS Control Tower com uma landing zone e OUs registradas para Sandbox, Desenvolvimento e Produção, cada uma com controles preventivos e detectivos habilitados. Toda semana as equipes pedem contas novas, hoje criadas por um script com a API do AWS Organizations que depois recebem trilhas, regras do AWS Config e acesso do IAM Identity Center por etapas avulsas, com erros frequentes. Qual solução padroniza a criação das contas com o MENOR esforço operacional?

Resposta: B) Provisionar as contas pelo Account Factory do Control Tower, escolhendo a OU registrada de destino, para que cada conta nasça com a baseline e os controles da OU

Por quê: No AWS Control Tower, o Account Factory é o caminho padrão para criar contas: ele provisiona a conta na OU registrada escolhida, aplica a baseline da landing zone e herda os controles da OU, preventivos (políticas da organização) e detectivos (regras do AWS Config). Ele pode ser usado pelo console, pelo Service Catalog ou por automação, como o Account Factory for Terraform.

Dica de prova: Contas novas já com baseline e controles = Account Factory do Control Tower; ambiente multi-conta governado desde o início = landing zone.

Referência: Provisionar contas com o Account Factory

Questão 10 de 12 · Domínio 2: Criação de arquiteturas resilientes

Um sistema legado de compensação bancária recebe conexões TCP em uma porta proprietária, e os bancos parceiros só liberam tráfego de saída para endereços IP fixos cadastrados em suas listas de permissões. A aplicação vai rodar em instâncias EC2 de um grupo do Auto Scaling distribuído por duas zonas de disponibilidade, e os IPs públicos divulgados não podem mudar quando instâncias forem substituídas. Qual solução atende a esses requisitos com alta disponibilidade?

Resposta: C) Criar um Network Load Balancer voltado para a internet com um Elastic IP em cada sub-rede habilitada e registrar o grupo no target group

Por quê: Quando clientes exigem IP fixo em listas de permissões, a solução altamente disponível é um Network Load Balancer com um Elastic IP por zona de disponibilidade (ou o AWS Global Accelerator, que fornece dois IPs anycast estáticos). Assim o endereço público pertence ao balanceador, e as instâncias podem ser trocadas pelo Auto Scaling sem impacto para os parceiros.

Dica de prova: IP estático na frente de várias instâncias: NLB com Elastic IP por AZ (ou Global Accelerator). ALB não tem IP fixo.

Referência: Zonas de disponibilidade do Network Load Balancer

Questão 11 de 12 · Domínio 3: Criação de arquiteturas de alto desempenho

Uma aplicação de análise em tempo quase real processa dados de sensores enviados continuamente para a AWS. Atualmente, os dados são gravados diretamente em uma tabela do Amazon RDS for PostgreSQL, e usuários reclamam de latência alta em consultas analíticas complexas. O arquiteto deseja manter ingestão em alta taxa, reduzir a latência das consultas e minimizar o impacto no banco transacional. Qual abordagem atende melhor a esses requisitos?

Resposta: B) Usar Data Firehose entregando ao S3 e consultas analíticas com o Athena

Por quê: Separar a camada analítica da transacional resolve o conflito. O Amazon Data Firehose recebe o fluxo dos sensores e o entrega no Amazon S3 em lotes de segundos a minutos, podendo converter para Parquet e particionar por data; em seguida, o Amazon Athena consulta os dados no S3, sem servidor e sem carga no RDS. Uma réplica de leitura não basta: a ingestão continua no RDS, e um banco orientado a linha segue lento para analytics em grande volume.

Dica de prova: Ingestão contínua com analytics pesado: Firehose para o S3 em Parquet particionado e consultas no Athena (ou Redshift). Não misture OLTP e OLAP no mesmo banco.

Referência: Conversão para Parquet no Amazon Data Firehose

Questão 12 de 12 · Domínio 4: Criação de arquiteturas com custo otimizado

Uma equipe de engenharia executa workloads de processamento em lote no Amazon ECS com tarefas Fargate On-Demand que rodam diariamente por cerca de 3 horas, com picos previsíveis e estáveis há mais de 8 meses. O workload não é crítico quanto ao tempo de conclusão (pode atrasar alguns minutos) e as tarefas podem ser reiniciadas se forem interrompidas, mas a empresa precisa reduzir significativamente os custos de computação sem reescrever a aplicação. Qual é a abordagem MAIS adequada e com melhor relação custo-benefício?

Resposta: C) Usar Fargate Spot, misturando tarefas Spot e On-Demand por estratégia de provedor

Por quê: O Fargate Spot executa tasks do ECS em capacidade ociosa da AWS com grande desconto sobre o Fargate On-Demand e pode interrompê-las com aviso de dois minutos. Para lotes que toleram reinício, uma capacity provider strategy que combina FARGATE (base mínima) e FARGATE_SPOT (maior peso) reduz bastante o custo sem mudar a aplicação nem gerenciar servidores. Compromissos como Compute Savings Plans cobram por hora o dia inteiro, o que pouco compensa para uma carga de 3 horas diárias.

Dica de prova: Lote tolerante a interrupção no Fargate: Fargate Spot via capacity provider strategy. EC2 Instance Savings Plans não cobrem Fargate; Compute Savings Plans cobrem.

Referência: Capacity providers do Fargate e do Fargate Spot
